# 구조 개요

GTG 아키텍처는 호스트가 호출하는 **플랫폼 훅**과, 훅 및 에이전트가 사용하는 **로컬 실행 코어** 두 영역으로 명확히 분리되어 있습니다. 코어는 모델 API나 외부 네트워크를 호출하지 않으며, 순수 Python 표준 라이브러리만으로 작업 상태, 완료 조건, 실행 증명서, 복구 수명주기를 관리합니다.

```
호스트(Antigravity / agy / Gemini CLI)
   │  훅 이벤트
   ▼
gtg/hooks.py ──▶ gtg/sessions.py ──▶ gtg/store.py  (SQLite + 파일 기반 실행 잠금)
   │                                      ▲
   │                                      │
   └── 안내 문구 gtg/context_message.py    │
                                          │
모델이 부르는 명령 ──▶ gtg/runner.py ──────┘
                          │
                          ├─ gtg/spec.py       계약 검증, 파일 지문, 감시 범위 예산
                          ├─ gtg/coverage.py   실제 실행 파일 관측
                          └─ gtg/certificate.py 증명서 생성과 재실행
```

## 계층 경계를 분리한 이유

인증, 모델 추론 호출, 샌드박스 보안은 전적으로 호스트 환경의 책임입니다. GTG는 이 영역에 개입하지 않습니다. 호스트별 차이점은 이벤트 명칭, 세션 식별 필드, 설치 경로, 타임아웃 단위 네 가지뿐이며, 이 모든 것은 [`gtg/platforms.py`](../../gtg/platforms.py)에 일원화되어 있습니다. 새로운 호스트를 추가 지원할 때도 해당 파일의 매핑 테이블만 확장하면 됩니다.

평가 및 채점 코드는 제품 구현 코드를 직접 임포트하지 않습니다. 순수 표준 라이브러리만을 사용하여, 제품 코드가 수정되더라도 채점 기준 자체가 함께 변조되는 사태를 구조적으로 방지했습니다. 이 격리 원칙은 단위 테스트를 통해 엄격히 유지됩니다.

내부 로직을 모델 ID로 분기하지 않습니다. 호스트에 설정된 모델을 그대로 사용하며, 검증되지 않은 외부 모델의 사고 수준이나 컨텍스트 윈도우 한도를 임의로 추정하지 않습니다.

## 모듈별 책임 정의

단일 모듈이 다중 책임을 갖지 않도록 모듈별 역할을 아래 표로 엄격히 규정합니다. 실제 소스 파일과 이 표가 어긋나면 아키텍처 검증 테스트가 실패합니다.

| 모듈 | 책임 |
| --- | --- |
| `gtg/platforms.py` | 호스트별 훅 이벤트·설치 경로·감지 표식의 단일 정의 |
| `gtg/spec.py` | 작업 계약 검증, 검증 대상의 지문과 범위 예산 |
| `gtg/store.py` | 작업·실행·메모의 SQLite 상태와 실행 중 여부를 알리는 파일 잠금 |
| `gtg/runner.py` | 검증 명령 실행과 현재 상태 조회 |
| `gtg/coverage.py` | 검사가 실제로 실행한 코드 파일 관찰 |
| `gtg/certificate.py` | 완료 증명서 생성과 상태 DB 없는 재실행 |
| `gtg/checkpoints.py` | 검증과 분리된 재개용 메모 |
| `gtg/sessions.py` | 호스트 세션 연결·재개 예산·중단 |
| `gtg/hooks.py` | 호스트 이벤트를 로컬 증거와 연결 |
| `gtg/context_message.py` | 훅 안내의 표현. IO 없음 |
| `gtg/discovery.py` | 읽기 전용 작업 후보 조회 |
| `gtg/inspection.py` | 여러 텍스트 파일의 범위 조회 |
| `gtg/package.py` | 호스트별 패키지 생성과 원문·훅 검증 |
| `gtg/install.py` | 호스트 감지·설치·검사·제거·복구 |
| `gtg/install_journal.py` | 파일 이동의 사전 기록과 되돌리기 |
| `gtg/legacy.py` | 구형 프로필 링크의 보존과 복구 |
| `gtg/__main__.py` | 에이전트가 쓰는 CLI 진입점 |

평가 프레임워크의 구조는 [평가 문서](../../evals/README.md)에 기술되어 있으며, 채점 로직은 제품 코드를 임포트하지 않습니다.

## 상태 저장소 및 격리 원칙

상태 관리는 작업공간 내 `.gtg/state.sqlite3` 단일 파일로 수행합니다. 보안을 위해 디렉터리는 `0700`, 파일은 `0600` 권한으로 생성하며, 내부에 `.gitignore`를 자동 배치하여 Git 추적 대상에 포함되지 않도록 차단합니다.

단일 작업 내에서 동시에 실행되는 검사는 오직 하나여야 한다는 불변식을 데이터베이스 유니크 인덱스로 강제합니다. 실행 중 상태 여부는 불안정한 프로세스 ID(PID)가 아니라, 프로세스 실행 중에만 유효한 파일 잠금(File Lock) 메커니즘으로 판별합니다. PID는 재부팅 후 타 프로세스에 재할당되거나 동일 OS 세션 내에서도 재사용되므로 확실한 신원 근거가 될 수 없습니다. 반면 OS 레벨 파일 잠금은 프로세스가 종료될 때 커널이 자동으로 해제하므로 정상 종료, 강제 종료(SIGKILL), 전원 차단, 재부팅 시나리오를 일관되게 포괄합니다. 자식 검사 프로세스가 잠금을 상속받으므로 부모 프로세스만 사망하고 검사만 남은 좀비 상황도 확실하게 감지할 수 있습니다.

## 패키징 및 설치 라이프사이클

단일 소스 원본에서 호스트별 패키지를 자동 빌드합니다. 배포 전 별도 임시 디렉터리에서 사전 무결성을 검증하고, 파일 이동 저널을 먼저 기록한 뒤 본 설치를 진행합니다. 설치 도중 프로세스가 비정상 종료되더라도 다음 실행 시 저널을 확인하여 잔여물을 안전하게 롤백 및 정리합니다.

패키지 배포물에는 전수 파일 SHA-256 해시 매니페스트가 포함됩니다. 배포된 시스템 지시문이 임의 변경되면 패키지 검증이 설치를 거부합니다. 또한 시스템 프롬프트에 숨겨진 제어 문자나 비가시적 유니코드(폭 없는 공백, Bidi 제어 문자 등)가 포함된 경우에도 즉시 거부됩니다.
