# 구조 개요

GTG는 호스트가 턴마다 부르는 **플랫폼 훅**과, 훅과 에이전트가 함께 쓰는 **로컬 실행 코어**로 나뉩니다. 코어는 모델 API나 외부 네트워크를 부르지 않고 Python 표준 라이브러리만으로 작업 상태와 완료 조건, 실행 증명서, 복구 과정을 다룹니다.

```
호스트(Antigravity / agy / Gemini CLI)
   │  훅 이벤트
   ▼
gtg/hooks.py ──▶ gtg/sessions.py ──▶ gtg/store.py  (SQLite + 파일 기반 실행 잠금)
   │                                      ▲
   ├── 안내 문구 gtg/context_message.py    │
   └── 교훈 기록 gtg/lessons.py            │
                                          │
모델이 부르는 명령 ──▶ gtg/runner.py ──────┘
   │                      ├─ gtg/spec.py       계약 검증, 파일 지문, 감시 범위 예산
   │                      ├─ gtg/coverage.py   실제 실행 파일 관측
   │                      └─ gtg/certificate.py 증명서 생성과 재실행
   │
   ├──▶ gtg/structure.py ──▶ gtg/changes.py (Git 변경 범위), gtg/code_shape.py (AST 측정)
   └──▶ gtg/prose.py ──▶ gtg/prose_registers.py (글 갈래별 규칙) ──▶ gtg/prose_patterns.py (표현 목록)
                     ├─▶ gtg/prose_rhythm.py (문장 리듬과 높임)
                     └─▶ gtg/prose_score.py (신호 밀도를 점수로)
```

## 경계를 나눈 이유

인증과 모델 호출, 샌드박스 보안은 호스트가 맡고 GTG는 여기에 끼어들지 않습니다. 호스트마다 다른 것은 이벤트 이름, 세션 식별 필드, 설치 경로, 시간 제한 단위 네 가지이고 모두 [`gtg/platforms.py`](../../gtg/platforms.py)에 모아 두었으므로, 새 호스트를 붙일 때도 이 파일의 표만 늘리면 됩니다.

평가·채점 코드는 제품 코드를 import하지 않고 표준 라이브러리만 씁니다. 제품 코드를 고쳐도 채점 기준이 따라 바뀌지 않게 하려는 것이고, 이 분리는 단위 시험으로 지킵니다.

내부 로직은 모델 ID로 갈라지지 않습니다. 호스트에 설정된 모델을 그대로 쓰고, 확인하지 않은 모델의 사고 수준이나 컨텍스트 한도를 짐작해 넣지 않습니다. 3.1에서 더한 구조·문체 검사도 어떤 모델이 쓴 코드와 글인지와 상관없이 같은 기준을 적용합니다.

3.2에서는 문체 검사를 글 갈래에 따라 나눴습니다. 같은 `~라고 볼 수 있다`도 논문에서는 관례이고 기술 문서에서는 흐린 문장이라, 갈래별 차이를 코드 분기 대신 [`gtg/prose_registers.py`](../../gtg/prose_registers.py)의 데이터로 둡니다. 문장 길이와 높임 등급 측정은 [`gtg/prose_rhythm.py`](../../gtg/prose_rhythm.py)로 옮겼고, `prose.py`에는 문서를 읽고 결과를 모으는 일만 남겼습니다. 점수 계산은 [`gtg/prose_score.py`](../../gtg/prose_score.py)가 따로 맡아서, 감점 가중치를 바꿔도 규칙 목록과 측정 코드는 그대로입니다.

## 모듈별 책임

모듈 하나가 여러 책임을 떠안지 않도록 책임을 아래 표에 한 문장으로 적습니다. 실제 소스 파일과 표가 어긋나면 아키텍처 시험이 실패합니다.

| 모듈 | 책임 |
| --- | --- |
| `gtg/platforms.py` | 호스트별 훅 이벤트·설치 경로·감지 표식의 단일 정의 |
| `gtg/spec.py` | 작업 계약 검증, 검증 대상의 지문과 범위 예산 |
| `gtg/code_contract.py` | 코드 작업의 빌드 선행 조건과 PRD 요구의 검사 연결 |
| `gtg/store.py` | 작업·실행·메모의 SQLite 상태와 실행 중 여부를 알리는 파일 잠금 |
| `gtg/runner.py` | 검증 명령 실행과 현재 상태 조회 |
| `gtg/coverage.py` | 검사가 실제로 실행한 코드 파일 관찰 |
| `gtg/certificate.py` | 완료 증명서 생성과 상태 DB 없는 재실행 |
| `gtg/checkpoints.py` | 검증과 분리된 재개용 메모 |
| `gtg/sessions.py` | 호스트 세션 연결·재개 예산·중단 |
| `gtg/hooks.py` | 호스트 이벤트를 로컬 증거와 연결 |
| `gtg/context_message.py` | 훅 안내의 표현. IO 없음 |
| `gtg/lessons.py` | 검증에서 드러난 교훈의 근거 확인·저장·최근 목록 조회 |
| `gtg/discovery.py` | 읽기 전용 작업 후보 조회 |
| `gtg/inspection.py` | 작업공간 텍스트 파일의 안전한 읽기와 범위 조회 |
| `gtg/environment.py` | 로컬 실행 환경 관찰과 명시한 필요조건 비교 |
| `gtg/testing.py` | Python 시험 관측의 유효성과 필수 시험 성공 확인 |
| `gtg/unittest_probe.py` | 별도 프로세스에서 unittest 실행과 시험별 성공 관측 |
| `gtg/changes.py` | Git 기준 리비전과 작업 트리의 변경 파일·추가된 줄 조회 |
| `gtg/code_shape.py` | Python 소스 하나의 정의·복잡도·응집도·빈 본문 측정. IO 없음 |
| `gtg/structure.py` | 변경 코드에 구조 기준을 적용한 차단·검토 신호 |
| `gtg/prose.py` | 문서를 읽어 표현과 리듬 신호를 줄 번호와 함께 모으기 |
| `gtg/prose_patterns.py` | 문체 검사가 찾는 공통 표현 목록. 로직 없음 |
| `gtg/prose_registers.py` | 학술·일상·문학 갈래별로 규칙을 끄고 완화하고 더하기 |
| `gtg/prose_rhythm.py` | 문장 길이·어미·첫머리·쉼표·높임 등급 측정 |
| `gtg/prose_score.py` | 찾은 신호의 밀도를 0~100점과 A~D 등급으로 환산 |
| `gtg/package.py` | 호스트별 패키지 생성과 원문·훅 검증 |
| `gtg/install.py` | 호스트 감지·설치·검사·제거·복구 |
| `gtg/install_journal.py` | 파일 이동의 사전 기록과 되돌리기 |
| `gtg/legacy.py` | 구형 프로필 링크의 보존과 복구 |
| `gtg/__main__.py` | 에이전트가 쓰는 CLI 진입점 |

평가 프레임워크 구조는 [평가 문서](../../evals/README.md)에 있고, 채점 로직은 제품 코드를 import하지 않습니다.

## 상태 저장소와 격리

상태는 작업공간의 `.gtg/state.sqlite3` 파일 하나에 둡니다. 폴더는 `0700`, 파일은 `0600` 권한으로 만들고 폴더 안에 `.gitignore`를 두어 Git 추적 목록에 나타나지 않게 합니다. 3.1에서 더한 교훈 기록 `.gtg/lessons.jsonl`도 같은 폴더를 씁니다.

한 작업에서 동시에 돌아가는 검사는 하나뿐이어야 하고, 데이터베이스 유니크 인덱스가 이를 막습니다. 검사가 아직 실행 중인지는 PID가 아니라 실행하는 동안만 유지되는 파일 잠금으로 판단합니다. PID는 재부팅 뒤 다른 프로세스에 다시 쓰이고 같은 세션 안에서도 재사용되어 신원 근거가 되지 못하지만, OS 파일 잠금은 프로세스가 끝나면 커널이 풀어 주기 때문입니다. 자식 검사 프로세스도 잠금을 물려받으므로 부모만 죽고 검사가 남은 경우도 알아챕니다. 정상 종료와 강제 종료(SIGKILL)는 시험으로 확인했지만, 실제 전원 차단과 그 뒤의 재부팅은 프로세스 강제 종료로 흉내 낸 시험까지만 했습니다.

## 패키징과 설치

호스트별 패키지는 한 원본에서 만듭니다. 설치 전에 따로 마련한 임시 폴더에서 패키지를 먼저 검증하고 파일 이동 기록을 남긴 뒤 실제 설치를 하므로, 도중에 프로세스가 죽어도 다음 실행에서 그 기록을 보고 남은 파일을 되돌립니다.

배포물에는 모든 파일의 SHA-256 목록이 들어 있어서, 배포된 지시문이 바뀌면 패키지 검증이 설치를 거부합니다. 지시문에 숨은 제어 문자나 폭 없는 공백, 양방향 제어 문자 같은 보이지 않는 유니코드가 있어도 거부합니다.
