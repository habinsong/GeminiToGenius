# 새 실행 구조 설계

본 문서는 GeminiToGenius의 아키텍처 설계 명세입니다. 이미 구현된 기능과 진행 상황은 진행 기록 및 단위 테스트를 통해 구분합니다.

## 기존 v2의 한계와 재개발 배경

과거 v2.15.0 프로필은 대부분 자연어 프롬프트 위주로 구성되어 있었습니다. 목표 관리, 진행 추적, 실패 복구, 검증 명령을 직접 실행하는 훅 프로세스가 부재했고, 단순 구조 검사만으로는 빈 훅 설정도 정상 상태로 오판하는 문제가 있었습니다. 이를 해결하기 위해 순수 Python 기반의 로컬 실행 코어로 전면 교체했습니다.

## 핵심 구조 및 설계 원칙

1. **간결한 진입 규칙**: 작업 범위 한정, 관련 코드 선행 분석, 실행 결과 검증, 토큰 비용 관리 원칙만 유지하며, 내장 도구 설명을 중복 기재하지 않습니다.
2. **역할별 전문 스킬**: 다단계 구현·진단, 최신 출처 조사, UI 검증 등 서로 다른 작업 절차만 선별 분리하며, 자연어 질의에 따라 호스트가 자율 선택하도록 합니다.
3. **로컬 실행 코어**: 모델 API나 네트워크 통신에 의존하지 않고, 순수 Python 표준 라이브러리만으로 작업 상태, 완료 조건, 실행 증거, 중단 사유를 관리합니다.
4. **플랫폼 어댑터**: Antigravity의 camelCase 이벤트와 Gemini CLI의 snake_case 이벤트를 각각 독립 파싱합니다. 인증, 모델 추론 호출, 샌드박스 보안은 전적으로 호스트가 담당합니다.
5. **패키징 및 설치기**: 단일 소스 원본에서 호스트별 패키지를 빌드합니다. 설치 전 사전 검증을 거치고, 저널링 기반 파일 이동을 통해 안전한 교체 및 롤백을 제공합니다.
6. **증거 기반 평가**: 실제 셸 명령의 종료 코드와 산출물 무결성을 직접 검증합니다. 선언된 완료 조건이 실제 요구사항을 충족하는지는 독립적인 벤치마크와 실험으로 평가합니다.

코드 탐색은 호스트 내장 도구를 우선 활용하며, 상태를 변경하지 않는 `inspect` 명령으로 여러 텍스트 파일을 원자적으로 읽을 수 있습니다. 라인 범위, 출력 길이 제한, 연속 조회 위치, 전체 파일 SHA-256 해시의 유효 범위를 명확히 구분합니다. 파일 조회 도중 내용이 변경되거나 경로가 치환되면 해당 결과를 즉시 폐기합니다.

평가 프레임워크는 제품 내부의 비공개 경로 판정 로직이나 프로세스 헬퍼를 임포트하지 않습니다. 순수 표준 라이브러리만 사용하여, 제품 내부 코드가 수정되더라도 평가 기준이 왜곡되지 않도록 분리했습니다.

호스트가 선택한 모델 설정을 그대로 따르며 모델 ID로 내부 로직을 분기하지 않습니다. 현재 Gemini 3.8 Flash뿐 아니라 차세대 Gemini 모델도 동일한 계약으로 실행합니다. 미확인 모델의 추론 수준이나 토큰 한도를 임의로 추정하지 않으며, 공식 사양과 호스트 지원 여부가 검증된 기능만 반영합니다.

## 상태 저장 및 완료 라이프사이클

작업 등록 시 최종 목표, 완료 조건, 감시 대상 파일, 고정된 검증 명령을 함께 정의합니다. 임의의 `echo passed` 같은 무의미한 명령이 실제 완료 조건을 대신할 수 없습니다. 실행기는 등록된 명령을 서브프로세스로 직접 호출하여 종료 코드, 소요 시간, 당시 파일 해시를 기록합니다.

모든 완료 조건이 현재 파일 상태에 대해 정상 통과해야 작업 완료를 선언할 수 있습니다. 검증 통과 후 코드가 수정되거나 검증 명령이 실패하면 이전의 성공 기록은 완료 근거로 인정되지 않습니다. 실행 도중 프로세스가 비정상 종료되거나 재시작된 경우에도 완료로 처리하지 않으며, 작업 간 상태 혼선을 방지하기 위해 고유 식별자를 격리합니다.

동일 세션에서 동일 작업을 중복 시작하면 기존 작업 인스턴스를 반환합니다. 작업 생성과 세션 바인딩을 단일 데이터베이스 트랜잭션으로 묶어 중복 생성 및 고아 작업 발생을 차단합니다. 작업 재개용 체크포인트는 별도 이력 테이블에 보존하며 실제 검증 판정에 영향을 주지 않습니다. 메모에 연결된 파일의 해시가 변경된 경우 재검증 필요 상태로 표시합니다.

새 세션에서는 `tasks` 명령이 읽기 전용으로 최근 작업 후보 목록을 제공합니다. 이때 표시되는 검사 통과 횟수는 과거 기록일 뿐 현재 시점의 무결성을 뜻하지 않습니다. `status` 명령으로 전체 명세와 현재 파일 무결성을 교차 확인하고, `attach` 명령으로 세션 연결만 안전하게 전환합니다.

## 중단 복구 및 리소스 예산 관리

사용자 취소, 권한 승인 대기, 호스트 예외, 쿼터 제한이 발생하면 작업을 무리하게 지속하지 않고 즉시 일시 중단합니다. 백그라운드 작업이 실행 중인 상태에서는 완료를 선언하지 않습니다. 모든 훅은 순수 로컬 연산만 수행하며 백그라운드 LLM 호출을 발생시키지 않습니다.

검증 CLI에 `SIGTERM` 또는 `SIGINT`가 수신되면 하위 프로세스 그룹을 안전하게 정리하고 중단 상태를 기록합니다. 부모 프로세스만 종료되고 자식 프로세스가 남아 있는 경우에도 성공으로 오판하지 않습니다.

자동 재개 예산이 소진되면 세션을 일시 정지하고 사유를 데이터베이스에 보존합니다. 중복 수신된 종료 이벤트는 진행 중인 재개를 취소하지 않으며, 이미 활성 상태인 연결에 대한 중복 호출은 예산을 추가 부여하지 않습니다.

다중 작업공간 환경에서는 동일한 호스트 세션 ID를 공유하는 로컬 작업들을 함께 추적합니다. 미완료 조건을 취합하고 일시 중지 상태와 재개 예산을 공유하며, 작업공간이 지정되지 않은 일반 대화에는 상태 데이터베이스를 생성하지 않습니다.

설치, 삭제, 복구 시 이루어지는 모든 파일 이동은 디스크 저널에 선행 기록됩니다. 미완료 저널이 감지되면 다음 실행 시 역순으로 롤백합니다. 사용자 정의 파일의 inode가 변경된 경우 덮어쓰지 않고 안전 백업 기록을 남깁니다.

## 신뢰 경계 (Security Boundaries)

외부 문서나 도구 출력은 단순 데이터일 뿐 시스템 명령으로 취급하지 않습니다. 플랫폼 훅은 원본 대화 내용이나 민감한 환경 변수를 로그에 복제하지 않습니다. 상태 파일은 안전한 로컬 디렉터리에만 보관하며 외부 경로를 가리키는 심볼릭 링크 접근을 차단합니다. 정규식 검사를 OS 수준의 샌드박스로 과장하지 않으며, 호스트 네이티브 도구의 보안 승인 체계를 우회하지 않습니다.

## 전환 및 배포 전략

기존 원본 아카이브를 보존하고 새 코어에 대한 완전한 테스트 스위트를 구축했습니다. 이후 독립된 임시 경로에서 패키지를 생성하여 설치, 실패, 복구 시나리오를 철저히 검증했습니다. 이 검증이 완료된 후 구형 프로필과 중복 사본을 정리하고 기본 설치 경로를 전환했습니다.

Python 표준 라이브러리만을 활용하여 외부 종속성을 완전히 제거했습니다. 플랫폼 훅 호출 시 발생하는 프로세스 기동 부하를 실측한 결과, 300개 소스 파일과 120개 테스트 파일 규모의 프로젝트에서 중앙값 102ms를 기록했습니다. 감시 범위 한계치에서의 파일 해시 재계산을 포함하더라도 1.2초 수준으로, 호스트 타임아웃 한도인 5초 이내를 안정적으로 충족합니다.
