# Antigravity CLI 호스트와 완료 증명서

확인일: 2026-09-08. 이 구간에서 실제 모델 요청은 0회입니다. 아래 결과는 로컬 파일·프로세스 실행으로만 얻었습니다.

## 확인한 공백

`gtg`는 `antigravity`와 `gemini-cli` 두 호스트만 만들었습니다. 새 테스트를 먼저 작성해 `build`, `destination`, `handle`이 `antigravity-cli`를 각각 거부하는 것을 재현했습니다. 완료 주장을 상태 DB 밖에서 재현할 방법도 없었습니다.

Gemini CLI는 2026-06-18부터 개인 계정 요청 처리를 중단했고 확장은 Antigravity 플러그인으로 이전합니다. 이 컴퓨터의 홈에는 GTG가 `~/.gemini/extensions/`에만 설치돼 있었고 `~/.gemini/antigravity-cli/`는 존재하지만 GTG가 없었습니다.

## 호스트 추가

- 호스트별 차이를 `gtg/platforms.py` 한 곳에 모았습니다. 이벤트 이름·설치 경로·감지 표식이 여기 있고 다른 모듈은 이 값을 참조합니다. 설치 이동 기록의 허용 경로도 같은 목록을 사용합니다.
- `antigravity-cli` 전역 설치 경로는 공식 문서의 `~/.gemini/antigravity-cli/plugins/<plugin_name>/`입니다. 워크스페이스 플러그인 폴더는 확인하지 못해 거부합니다.
- 훅 계약은 데스크톱과 같습니다. 임시 홈에 실제로 설치한 뒤 `PreInvocation`과 `Stop` 훅 두 개를 실행해 세션 안내와 `decision: stop`을 확인했습니다.
- 데스크톱 플러그인과 CLI 플러그인을 같은 홈에 함께 설치해도 서로의 원문과 manifest를 바꾸지 않는 것을 확인했습니다.

## 한 번의 명령으로 감지·설치·검사·제거

- 호스트가 직접 만드는 설정 파일만 감지 근거로 사용합니다. GTG가 만든 폴더는 근거가 아니라는 것을 테스트로 고정했습니다.
- 표식 두 개를 만든 임시 홈에서 `install.sh` 한 번이 두 호스트에 설치하고 각각 훅 2개를 실행했습니다. 이어서 `doctor`가 두 호스트를 검사하고 `uninstall`이 두 호스트를 보존 경로로 옮겼습니다.
- 한 호스트 경로에 사용자 파일이 있어 설치가 거부되는 경우도 시험했습니다. 나머지 호스트는 성공하고 전체 종료 코드는 1이며 사용자 파일은 그대로 남았습니다.
- 이 컴퓨터의 실제 홈에서는 읽기 전용 조회만 했습니다. 감지 결과는 `antigravity`, `antigravity-cli`이고 현재 설치는 `antigravity`, `gemini-cli`입니다. 사용자 환경은 바꾸지 않았습니다.

## 완료 증명서와 재실행

- `gtg/certificate.py`는 완료 조건마다 실제 실행한 명령·종료 코드·검증 대상 파일 지문을 한 문서로 묶고 본문 해시를 붙입니다. 통과하지 않은 검사에는 지문을 붙이지 않습니다.
- `replay`는 상태 DB를 읽지도 만들지도 않습니다. 설치된 패키지에서 상태 DB를 지운 뒤 증명서만으로 명령을 다시 실행해 두 검사가 재현되는 것을 확인했습니다.
- 검증 대상 파일을 고치면 `reason: "fingerprint"`로 재현이 깨지고, 검사 명령이 실패하면 `reason: "returncode"`가 됩니다. 본문을 고치면 해시 불일치로 거부합니다.
- 증명서에 기록된 작업공간과 다른 폴더에서는 명령을 실행하지 않습니다. 사용자가 `--trust-commands`를 지정할 때만 실행하고 `workspace_matches: false`로 표시합니다.
- 미검증 작업의 `certify`는 종료 코드 1과 `verified: false`를 반환합니다.

## 범위와 한계

증명서는 등록된 검사 범위의 재현 가능성만 보여 줍니다. 검사 설계가 사용자 요구를 모두 담았는지는 증명하지 않습니다. `agy` 실행 파일은 이 컴퓨터에 없으므로 실제 CLI의 플러그인 발견·훅 발행·스킬 자동 선택은 미검증입니다. `agents/` 서브에이전트 정의는 형식을 확인하기 전까지 만들지 않았습니다.
