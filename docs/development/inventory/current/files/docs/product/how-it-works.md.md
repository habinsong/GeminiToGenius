# 동작 방식

사용자는 평소처럼 요청합니다. 나머지는 모델과 훅이 합니다.

```
사용자 요청
   ↓
턴 시작 훅 — 확인된 세션 값과 남은 미검증 상태를 전달
   ↓
모델이 판단 — 여러 턴에 걸칠 작업이면 완료 조건을 고정해 등록
   ↓
verify — 등록한 명령을 실제로 실행하고 종료 코드·파일 지문을 남김
   ↓
턴 종료 훅 — 미검증이면 남은 예산 안에서 되돌림
   ↓
certify — 주장과 근거를 한 파일로 묶음
```

## 완료 조건을 먼저 고정합니다

모델이 요청을 읽고 `.gtg/task.json`에 검사를 씁니다. 무엇을 실행하면 이 요청이 끝난 것인지를 미리 적는 것입니다. 등록한 뒤에는 그 명령을 바꿀 수 없습니다. 나중에 통과하기 쉬운 쪽으로 조건을 옮기지 못하게 하려는 것입니다.

형식은 [작업 명세](../reference/task-spec.md)에 있습니다.

## 검사는 실제로 돌립니다

`verify`가 등록된 명령을 그대로 실행합니다. 출력은 호스트로 흘려보내고, 종료 코드와 걸린 시간과 검증 대상 파일의 해시를 로컬에 남깁니다. 실행하지 않은 검사를 통과로 만들 방법은 없습니다.

통과한 검사라도 대상 파일이 바뀌면 `stale`이 됩니다. 저장된 성공을 현재 상태의 근거로 쓰지 않습니다.

## 끝났다고 말할 때 근거를 함께 냅니다

`certify`가 실행한 명령, 종료 코드, 파일 지문을 한 문서로 묶습니다. 받는 쪽은 상태 DB 없이 `replay` 하나로 다시 확인합니다. 판정은 `pass`, `invalid`, `inconclusive` 셋이며 미확정을 통과로 바꾸지 않습니다.

자세한 것은 [완료 증명서](../reference/certificate.md)에 있습니다.

## 무엇을 검증하지 못했는지도 냅니다

검사를 돌리는 동안 어떤 코드 파일이 실제로 실행됐는지 관찰합니다. 통과한 검사가 한 번도 실행하지 않은 파일이 있으면 그대로 보고합니다. 관찰할 수 없는 언어가 범위에 있으면 미실행을 주장하지 않고, 무엇이 판단을 막았는지 밝힙니다.

[실행 관측](../architecture/coverage.md)에 방법과 한계가 있습니다.

## 여러 턴에 걸쳐 이어집니다

턴이 끝날 때 미검증 상태가 남아 있으면 훅이 남은 예산 안에서 되돌립니다. 기본 2회입니다. 자동 재개는 사용자 쿼터를 쓰므로 무한히 하지 않습니다.

세션이 끊겨도 작업은 남습니다. 새 세션에서 `tasks`로 찾아 `attach`하면 같은 완료 조건과 검사 결과, 메모를 그대로 이어받습니다. 긴 작업 중간에는 `checkpoint`로 재개용 메모를 남깁니다. 메모는 기록일 뿐 검사 성공을 대신하지 않습니다.

## 언제 발동하나

모든 요청에 작업을 등록하지는 않습니다. 지시문은 여러 턴에 걸칠 변경 작업에만 등록하라고 말합니다. 파일 하나 고치는 요청에 완료 조건과 증명서를 붙이면 비용만 늘기 때문입니다.

실측에서는 20회 중 5회 등록했습니다. 등록한 5회는 모두 검사를 실행하고 증명서를 남겼지만, 등록하지 않은 짧은 작업에서는 GTG가 있으나 없으나 결과가 같았습니다. [측정 결과](../verification/README.md)에 그대로 적어 두었습니다.
