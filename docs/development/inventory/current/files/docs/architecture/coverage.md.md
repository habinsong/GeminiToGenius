# 실행 관측

검사를 돌릴 때 어떤 코드 파일이 실제로 실행됐는지 함께 기록합니다. 통과한 검사가 무엇을 건드리지 않았는지 드러내기 위한 것입니다.

## 방법

Python은 임시 폴더의 `sitecustomize.py`를 `PYTHONPATH` 앞에 두어 인터프리터 시작 시점에 붙습니다. `sys.monitoring`의 `PY_START`만 쓰고 콜백에서 바로 `DISABLE`을 돌려주므로, 이미 본 코드 위치는 계측이 꺼집니다. `sys.monitoring`이 없으면 `sys.settrace`로 물러납니다.

Node는 `--require`로 넣은 부트스트랩이 `module.registerHooks`의 `load`를 걸어 실행된 파일을 모읍니다.

검사가 만든 하위 프로세스도 같은 방식으로 관찰됩니다.

기존 `sitecustomize`를 가리지 않습니다. 남은 경로에서 원본을 찾아 이어서 실행하며, 관측기 안에서 관측기가 또 돌아도 사용자 파일을 건너뛰지 않습니다.

## 관찰할 수 있는 것

| 확장자 | 상태 |
|---|---|
| `.py`, `.js`, `.mjs`, `.cjs` | 관찰합니다. |
| `.ts`, `.mts`, `.cts` | 런타임이 직접 실행할 때만 관찰합니다. |
| `.tsx`, `.jsx`, `.go`, `.rs`, `.sh` 등 | 관찰하지 않습니다. |

TypeScript는 처음에 관찰 불가로 분류했다가, Node 26이 `.ts`를 직접 실행하고 훅이 그 파일을 기록하는 것을 실험으로 확인해 바꿨습니다. 컴파일 산출물을 실행한 경우에는 원본 TypeScript의 미실행을 주장하지 않습니다.

셸 스크립트는 일부러 관찰하지 않습니다. `BASH_ENV`와 DEBUG 트랩으로는 `source`한 파일을 놓치고, 놓치지 않으려면 사용자 스크립트의 동작을 바꾸는 옵션을 켜야 합니다. `/bin/sh`는 `BASH_ENV`를 아예 무시합니다. 부분 관찰은 실행한 파일을 미실행으로 잘못 보고하므로 하지 않는 편이 낫습니다.

## 나오는 값

| 필드 | 뜻 |
|---|---|
| `executed_watch` | 이 검사가 실제로 실행한 검증 대상 |
| `unexecuted_watch` | 통과했는데 한 번도 실행하지 않은 검증 대상 |
| `unobservable_watch` | 위 판단을 막은 파일. 셸 스크립트 하나만 범위에 있어도 목록 전체를 만들 수 없습니다. |

`unexecuted_watch`가 `null`이면 두 경우입니다. 관찰할 수 없는 언어가 범위에 있거나, 범위가 너무 커서 다 세지 못한 것입니다. 앞의 경우에만 `unobservable_watch`가 채워집니다. 검사를 나눠 관찰 가능한 범위만 따로 등록하면 나머지의 미실행 목록을 얻을 수 있습니다.

## 한계

파일 단위입니다. 실행했다는 것이 그 파일의 모든 동작을 검증했다는 뜻은 아니고, 줄이나 분기 수준의 커버리지도 아닙니다. 같은 내용을 다른 경로에서 실행하면 원본은 미실행으로 나옵니다. 문서나 설정 같은 비실행 파일은 대상이 아닙니다.
