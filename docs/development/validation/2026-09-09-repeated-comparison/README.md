# 반복 실행 경쟁 비교: 4개 팔 × 8사례 × 2회

확인일: 2026-09-09. 사용자 승인으로 실제 쿼터를 사용했습니다. 총 64회 실제 실행이며 모두 같은 요청·같은 채점기를 씁니다. `comparable: true`, 막힌 이유 없음.

## 팔

| 팔 | 환경 | 모델 | GTG |
| --- | --- | --- | --- |
| `agy-gtg` | Antigravity CLI 1.1.28 헤드리스 | `gemini-3.8-flash-high` | 전역 등록·활성 |
| `agy-plain` | 같은 CLI·같은 모델 | `gemini-3.8-flash-high` | `agy plugin disable`로 비활성 |
| `claude-code` | Claude Code 2.1.265 | `claude-sonnet-5` | 없음 |
| `codex-cli` | Codex CLI 0.137.0 | `gpt-5.6-terra` | 없음 |

앞의 두 팔이 핵심입니다. **호스트·모델·요청·채점기가 모두 같고 GTG만 다릅니다.** 이 쌍만이 GTG의 기여를 분리합니다. 뒤의 두 팔은 제품 간 참고이며 모델이 달라 우열 근거가 되지 못합니다.

경쟁 팔에는 권한을 넉넉히 줬습니다(`--permission-mode bypassPermissions`, `-s workspace-write`). 상대를 불리하게 만든 비교는 근거가 못 됩니다.

## 결론: GTG의 산출물 이점은 확인되지 않았습니다

**`agy-gtg`와 `agy-plain`이 14/14로 완전히 같습니다.** 매번 통과한 사례도 7/7로 같습니다. 같은 모델에서 GTG를 켜고 끈 차이가 산출물 결과에 나타나지 않았습니다. 평균 소요는 GTG 쪽이 7초 깁니다.

이 결과를 유리하게 해석하지 않습니다. 이 자료로 "GTG가 더 낫다"고 말할 수 없습니다.

## 왜 차이가 없었나: 모델이 GTG를 대부분 쓰지 않았습니다

각 시행의 `.gtg/state.sqlite3`를 직접 열어 확인했습니다.

**16번 중 5번만 작업을 등록했습니다.** 나머지 11번은 상태 DB조차 만들지 않았습니다.

| 시행 | 작업 | 검사 실행 | 통과 | 메모 | 증명서 |
| --- | --- | --- | --- | --- | --- |

즉 `agy-gtg` 팔은 대부분의 시행에서 사실상 `agy-plain`과 같은 것을 실행했습니다. 두 팔의 점수가 같은 것은 당연한 결과입니다.

**동작했을 때는 설계대로 동작했습니다.** 등록한 5회 모두 검사를 실제로 실행해 통과시켰고 증명서를 만들었습니다. 이전 진행 상태가 있던 `resume-export`에서는 두 작업을 연결하고 메모까지 남겼습니다.

이것이 이번 비교에서 나온 가장 실행 가능한 결론입니다. 문제는 **작동 여부가 아니라 발동 조건**입니다. 현재 지시문은 "복잡한 변경 작업"에만 등록하라고 하고 "단순 요청에는 작업 등록이 필요 없습니다"라고 적습니다. 이 평가 사례들은 파일 두세 개짜리라 모델이 단순으로 판단한 것이 무리가 아닙니다.

## 이 평가 묶음은 변별력이 거의 없습니다

자동 채점 7사례 중 6개를 **네 팔 모두 2/2로 통과**했습니다. 변별한 사례는 `resume-export` 하나뿐이고, 그마저 `agy-gtg`와 `agy-plain`이 똑같이 2/2라 GTG가 아니라 호스트·모델 차이를 가릅니다. 천장에 붙은 묶음으로는 어떤 하네스 차이도 잴 수 없습니다. 더 어려운 사례가 필요합니다.

## 도중에 고친 측정 결함

처음 관측값에서 `agy-gtg`의 "실행한 작업공간 파일"이 14개, `claude-code`가 2개로 나왔습니다. 확인해 보니 **14개 중 12개가 작업공간에 설치된 GTG 자기 모듈**(`.agents/plugins/geminitogenius/gtg/*.py`)이었고 과제 코드 실행은 양쪽 다 2개로 같았습니다.

`runs_that_executed_code`가 이대로면 **하네스를 설치한 팔은 검사를 한 번도 돌리지 않아도 "코드를 실행했다"로 세어집니다.** GTG에게 유리한 방향의 측정 오류입니다. `evals/execution.py`의 실행 관측에서 `.agents`를 제외했습니다. 채점의 범위 감시는 그대로 두어, 설치된 하네스를 고쳐 검사를 무력화하는 시도는 계속 잡힙니다(두 성질 모두 시험으로 고정).

이 수정은 `definition_digest`를 바꾸므로 배치가 끝난 뒤에 적용했습니다. 위 표의 "과제 코드 실행" 열은 기록된 파일 목록에서 사후 보정한 값입니다.

## 배치가 잘못 센 것

처음 집계에서 `inspect-only`를 네 팔 모두의 실패로 셌습니다. 이 사례는 `requires_human_review: true`라 **설계상 자동 통과가 불가능**합니다. 실패가 아니라 사람 검토 대상입니다. 네 팔 모두 `scope_passed: true`로 지시대로 파일을 건드리지 않았고, 답변을 직접 읽어 보니 넷 다 원인(`clamp`가 `min(value, upper)`만 호출해 하한 미적용)을 정확히 짚었습니다. Claude Code는 README의 `ValueError` 규칙 누락까지 언급해 가장 상세했습니다.

## 한계

- 사례 8개·시행 2회입니다. 통계적 결론을 낼 규모가 아닙니다.
- 모델이 팔마다 다릅니다. `claude-code`·`codex-cli`와의 비교는 제품과 모델이 섞여 있어 우열 근거가 되지 못합니다.
- 토큰 사용량과 비용은 수집하지 않았습니다. 벽시계 시간만 있습니다.
- `resume-export`는 `gtg` 프로필에서만 이전 진행 상태를 심습니다. 다만 `agy-plain`도 2/2로 통과해 이 비대칭이 결과를 가르지는 않았습니다.
- `agy-plain`의 GTG 비활성은 `agy plugin disable` 실행과, 모델이 GTG 메시지를 받지 못했다고 답한 것으로 확인했습니다. 훅 미발행을 직접 관측하지는 않았습니다.

## 덧붙임: 변별 사례를 만들어 다시 재 봤습니다

위 결과가 "평가 묶음에 변별력이 없어서"인지 확인하려고, 검증을 실제로 돌려야 통과하는 사례 두 개를 새로 만들었습니다.

- `test-encodes-bug`: 딸려 온 테스트가 버그를 정답으로 굳혀 두었습니다. 테스트는 초록인데 README 규칙과 어긋납니다. 코드만 고치면 그 테스트가 빨개집니다.
- `cross-module-break`: 한 모듈의 표시 형식을 고치면 다른 모듈의 테스트가 깨집니다.

두 사례 모두 손대지 않으면 실패하고, 코드만 고치고 검사를 두고 가면 실패하며, 올바른 수정이면 통과하는 것을 실제 쿼터를 쓰기 전에 확인했습니다.

그리고 같은 모델에서 GTG를 켜고 끄고 각각 2회씩 돌렸습니다.

| 팔 | 통과 | 작업 등록 |
| --- | --- | --- |
| `agy-gtg` | 4/4 | 0/4 |
| `agy-plain` | 4/4 | — |

**또 같습니다.** 함정은 살아 있지만 이 모델은 GTG 없이도 스스로 테스트를 돌려 모순을 발견하고 양쪽을 고쳤습니다. 그리고 GTG 팔의 4회 모두 작업을 등록하지 않았습니다. 앞선 5/16과 합치면 20회 중 5회입니다.

정리하면 이렇습니다. 파일 두세 개짜리 작업에서는 좋은 모델이 알아서 검증하고, GTG는 발동하지도 않으며, 발동해도 결과가 달라지지 않습니다. GTG가 값을 하려면 **한 턴에 끝나지 않는 작업**이어야 합니다. 실제로 유일하게 GTG가 매번 발동한 사례는 이전 세션의 진행 상태를 이어받는 `resume-export`였고, 거기서는 작업 두 개를 연결하고 메모와 증명서를 남겼습니다. 다음 사례는 그 방향으로 만들어야 합니다.
