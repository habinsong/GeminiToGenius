# 재부팅 뒤 중단 복구를 PID가 아닌 잠금으로 판단

확인일: 2026-09-09. 실제 모델 요청은 0회입니다. 로컬 프로세스 실험만 사용했습니다.

## 무엇이 고장이었나

`남은 작업`에 "전원 차단 복구 미검증"으로 남아 있던 항목을 실제로 실행해 봤습니다. 고장이 재현됐습니다.

`Store.recover`는 `os.kill(owner_pid, 0)`으로 검사 소유 프로세스의 생존을 판단했습니다. **PID는 재부팅하면 1부터 다시 배정되고 같은 부팅 안에서도 재사용됩니다.** 그래서 기록된 PID가 전혀 다른 프로세스를 가리킬 수 있습니다.

재부팅 직후 상태(`owner_pid`가 살아 있는 다른 프로세스를 가리킴)를 만들어 실행한 결과입니다.

```
--- 2) 재부팅 뒤 PID 재사용(owner_pid=1, launchd) ---
종료 코드: 1
응답: {"ok": false, "error": "[Errno 1] Operation not permitted"}

--- 3) 같은 상태에서 검사를 다시 실행 ---
종료 코드: 1
응답: {"ok": false, "error": "이미 실행 중인 검사가 있습니다. 완료되거나 중단 복구가 필요합니다."}
```

두 가지 결함이 함께 드러났습니다.

1. **영구 교착.** `recover`는 실패하고 `verify`는 "이미 실행 중"이라며 거부합니다. 사용자가 상태 DB를 직접 수정하지 않는 한 그 작업은 다시 진행되지 않습니다. 노트북을 재부팅하고 이어서 작업하는 것은 이 하네스의 정상 사용 경로이므로 실제로 만나는 고장입니다.
2. **원시 errno 노출.** `os.kill`은 다른 사용자 소유 PID에 `PermissionError`(EPERM)를 던지는데 코드가 `ProcessLookupError`만 잡아 `[Errno 1] Operation not permitted`가 그대로 나왔습니다. `gtg/runner.py`의 `group_alive`·`terminate`에도 같은 경로가 있었고, 그중 `finally` 안의 호출은 아무도 잡지 않았습니다.

## 왜 잠금인가

PID로는 신원을 확인할 수 없습니다. 부팅 시각(`kern.boottime`, `/proc/stat btime`)을 함께 기록하는 방법도 검토했지만, macOS의 `kern.boottime`은 시계 보정으로 값이 움직일 수 있어 "재부팅했는가"를 오차 허용치로 추정해야 합니다. 추정을 쓰지 않기로 했습니다.

대신 **실행하는 동안만 유지되는 파일 잠금**을 씁니다. OS가 프로세스 종료 시 자동으로 풀어 주므로 정상 종료·강제 종료·전원 차단·재부팅을 모두 같은 방식으로 덮습니다. 채택 전에 이 기계에서 의미를 직접 측정했습니다.

```
1) 아무도 안 잡았을 때 held: False
2) 소유자가 잡은 뒤 held: True (소유자 15416 자식 15417 )
3) 소유자만 SIGKILL 한 뒤 held: True   <- 자식이 fd를 상속했으면 True
4) 자식까지 종료한 뒤 held: False   <- 모두 죽으면 False
5) 단독 소유자 held: True
6) SIGKILL 뒤 held: False   <- 전원 차단과 같은 비정상 종료에서 해제
7) 같은 프로세스의 다른 fd에서 본 held: True   <- 같은 프로세스라도 별개 fd면 True
```

(3)이 핵심입니다. 검사 프로세스가 잠금 fd를 물려받으므로, 소유자가 죽고 검사만 남은 상태도 **PID 없이** 그대로 드러납니다. 종전에 `child_pid`로 따로 처리하던 경우가 같은 신호로 합쳐집니다. 잠금 충돌은 `BlockingIOError`(errno 35)로 구분됩니다.

## 구현

- `gtg/store.py`에 `lock_path`·`hold`·`running`·`pid_alive`를 두고, `begin`이 `.gtg/runs/<run_id>.lock`을 잡고 `finish`·`close`가 풉니다.
- `gtg/runner.py`의 검사 실행이 `pass_fds=store.inherited(run_id)`로 잠금을 물려줍니다.
- `Store.alive`는 잠금을 먼저 봅니다. 잠금 기록이 없는 예전 실행에만 PID로 물러나며, 그 경로에서도 EPERM은 "우리 프로세스가 아님"으로 처리해 오류를 흘리지 않습니다.
- `fcntl`이 없는 환경(윈도우)과 잠금을 만들 수 없는 파일 시스템에서는 종전 PID 판단을 유지합니다. 잠금을 못 쓰는 것을 실행 중이라고 주장하지 않습니다.

## 고친 뒤 같은 시나리오

```
--- 2) 재부팅 뒤 PID 재사용(owner_pid=1, launchd) ---
종료 코드: 0
응답: "recovered": 1 ... "status": "interrupted"

--- 3) 같은 상태에서 검사를 다시 실행 ---
종료 코드: 0
```

복구가 되고 작업이 이어집니다. 반대 방향도 확인했습니다. 검사 프로세스가 아직 살아 있으면 복구를 거부하고, 그 프로세스를 끝내면 복구됩니다(`tests/test_runtime.py`).

## 남은 한계

- 실제 전원 차단이 아니라 강제 종료로 확인했습니다. 잠금은 커널이 관리하고 디스크에 남지 않으므로 재부팅 뒤에는 항상 풀린 상태입니다. 다만 실제 전원 차단으로 재부팅한 기계에서의 확인은 아직 없습니다.
- 네트워크 파일 시스템에서 `flock`이 신뢰할 수 없는 경우 `running`은 판단 불가(`None`)로 물러납니다. 이 경로는 실제 NFS·SMB에서 확인하지 않았습니다.
- 윈도우 경로는 여전히 PID 판단이며 미검증입니다.
