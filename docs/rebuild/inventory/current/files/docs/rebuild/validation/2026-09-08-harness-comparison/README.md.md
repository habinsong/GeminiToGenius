# 통제된 하네스 비교 프로토콜

확인일: 2026-09-08. 실제 모델 요청은 0회입니다. 아래 결과는 참조 수정과 실제 채점기로만 얻었습니다.

## 왜 필요한가

원래 목표에는 다른 에이전틱 환경보다 나은 결과가 포함됩니다. 지금까지 평가 도구는 한 번의 시행을 준비·채점할 수 있었지만 여러 하네스의 결과를 같은 조건에서 모으는 방법이 없었습니다. 공개 연구는 하네스를 평가의 독립 축으로 두고 작업 환경·예산·시간 제한·채점기를 고정한 채 각 하네스의 실제 실행 방식을 유지하라고 정리합니다.

## 구현

`evals/comparison.py`의 `compare`와 `python3 -m evals.harness compare`를 추가했습니다. `prepare`에는 `--arm`, `--model` 라벨을 추가했습니다. `--profile`은 GTG 설치 여부를 정하고, `--arm`은 어떤 하네스로 실행했는지 사용자가 선언하는 라벨입니다.

조건이 하나라도 다르면 비교 결과를 만들지 않고 막힌 이유를 그대로 보고합니다.

| 막는 이유 | 뜻 |
| --- | --- |
| `single_arm` | 비교 대상이 한 구성뿐입니다. |
| `definition_digest` | 채점 기준 원문이 시행마다 다릅니다. |
| `prompt_sha256` | 같은 사례인데 보낸 요청이 다릅니다. |
| `case_coverage` | 구성마다 수행한 사례 집합이 다릅니다. |
| `ungraded` | 채점하지 않은 시행이 있습니다. 패배로 세지 않습니다. |
| `unstable_grades` | 같은 시행의 채점 결과가 엇갈립니다. 한쪽을 고르지 않습니다. |

집계는 `(arm, model)` 단위입니다. 같은 하네스라도 모델이 다르면 따로 셉니다.

## 실제 실행

두 시행을 준비하고 한쪽에만 참조 수정을 적용한 뒤 실제 CLI로 채점·비교했습니다. 참조 수정은 스크립트가 수행했으며 모델 성능 결과가 아닙니다.

- [정상 비교](comparison-clean.json): `comparable: true`, `demo-fixed` 1/1 통과, `demo-nofix` 0/1입니다. 두 구성의 사례·요청·채점 기준이 같습니다.
- [엇갈린 채점 차단](comparison-unstable.json): 같은 시행을 수정 전후로 두 번 채점하자 `unstable_grades`로 비교를 막고 통과로 세지 않았습니다. 나중 결과를 조용히 채택하지 않습니다.

첫 참조 수정이 하한·상한 역전 입력의 `ValueError` 요구를 놓쳐 채점이 실패한 것도 확인했습니다. 채점기가 요구를 실제로 검사한다는 증거입니다.

## 한계

이 도구는 어떤 하네스가 실제로 실행됐는지 확인하지 않습니다. `arm`과 `model`은 사용자가 선언한 라벨이며 보고서에도 그렇게 표시합니다. 토큰 사용량·비용·지연은 수집하지 않습니다. 실제 Codex·Claude Code·OmO와의 비교 실행은 아직 하지 않았고, 사례 5개는 진단용이며 공개 벤치마크 대체가 아닙니다. 그러므로 이 구간은 비교를 **가능하게** 만든 것이며 우월성을 입증한 것이 아닙니다.
