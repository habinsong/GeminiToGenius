# 실행 중인 검사가 완료 보고를 막지 못하던 구멍

확인일: 2026-09-09. 실제 모델 요청은 0회입니다. 실제 훅 프로세스에 공식 계약대로 만든 입력을 넣어 확인했습니다.

## 어떻게 발견했나

훅은 사용자의 실제 세션에서 매 턴 실행되므로, 나쁜 조건을 실제로 만들어 응답을 확인했습니다. 한 작업에 대해 Stop 훅을 세 시점에 호출했습니다.

```
[검사 실행 전(미검증)] 75ms  {"decision": "continue", "reason": "GTG 미완료 상태(데이터): ..."}
[검사 실행 중]        83ms  {"decision": "stop"}
[검사 통과 뒤]        75ms  {"decision": "stop"}
```

가운데가 틀렸습니다. 검사가 **실행 중**이면 아무것도 검증되지 않았는데 훅이 종료를 조용히 허용했습니다. 이 하네스가 존재하는 이유인 "미검증을 완료로 보고하지 못하게 한다"가 그 구간에서 통하지 않았습니다.

처음 만든 입력은 필드 이름이 틀려(`workspaceRoots`·`sessionId`) 훅이 입력 검증에서 되돌아갔고, 그 상태의 응답을 정상 동작으로 오해할 뻔했습니다. 공식 계약의 `workspacePaths`·`conversationId`로 고쳐 다시 측정한 값이 위 결과입니다. 같은 이유로 이전에 기록한 "훅 왕복 20ms"는 인자 오류 경로의 값이었습니다. 정상 경로는 75~90ms입니다.

## 원인

`gtg/hooks.py`의 `resume()` 첫 줄이 두 개의 다른 결정을 한 값으로 합쳤습니다.

```python
if any(check["status"] == "running" ...):
    return empty      # empty == {"decision": "stop"}
```

앞의 판단("실행 중인 검사를 재개로 중복 실행하지 않는다")은 옳습니다. 재개는 사용자 쿼터를 쓰고 이미 도는 검사를 겹치게 합니다. 그러나 그 결론을 `empty`, 즉 **종료 허용**으로 돌려주면서 뒤의 판단("미검증을 완료로 통과시키지 않는다")까지 함께 버렸습니다.

이 상태는 드물지 않습니다. 검사를 배경으로 돌린 경우, 사용자가 터미널에서 따로 검증을 돌리는 경우, 그리고 **중단된 실행이 `finished IS NULL` 기록을 남긴 경우**가 모두 여기에 걸립니다. 마지막 경우는 `recover` 전까지 영구히 지속되므로, 그 작업의 모든 완료 보고가 계속 조용히 허용됩니다.

기존 검사 308개 중 이 경로를 덮는 것이 하나도 없었습니다.

## 고침

`still_running`으로 두 결정을 분리했습니다. 재개는 그대로 하지 않고(예산 소비 0), 종료에는 이유를 붙입니다.

```
[검사 실행 중] 90ms {"decision": "stop", "reason": "GTG: 등록된 검사가 아직 실행 중이라 완료가
검증되지 않았습니다(slow). 자동 재개는 하지 않습니다. 검사 결과를 확인하고, 중단된 실행이면
recover 뒤 다시 검증하세요."}
```

`{"decision": "stop", "reason": ...}`은 재개 상한 도달 시 이미 쓰던 형식입니다. 이번 변경은 원래 내보내던 종료에 이유를 더한 것뿐이라, 호스트가 `reason`을 무시해도 동작은 종전과 같습니다.

회귀 검사 두 개를 추가했고, 고치기 전 동작으로 되돌려 둘 다 실패하는 것을 확인했습니다.

## 남은 한계

Gemini CLI(`AfterAgent`)에는 **종료를 막지 않으면서 사실만 전달하는** 출력 형식을 확인하지 못했습니다. `continue: false`는 종료를 차단하므로 이 상황에 맞지 않습니다. 확인하지 못한 필드를 가정해 쓰지 않고, 해당 호스트는 종전대로 빈 허용을 유지했습니다. 이 비대칭은 실제 호스트에서 확인한 뒤에 없앱니다.

Antigravity의 `reason` 문자열이 실호스트 화면에 어떻게 표시되는지는 확인하지 않았습니다. 값이 무시되어도 종전 동작과 같으므로 위험은 없습니다.
