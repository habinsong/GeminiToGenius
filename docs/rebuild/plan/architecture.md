# 새 실행 구조

이 문서는 설계입니다. 구현된 항목은 진행 기록과 테스트로 구분합니다.

## 재개발 전 문제

v2.15.0 프로필은 대부분 프롬프트였습니다. 목표·진행·실패·검증 결과를 다루던 훅 실행 파일은 없었고, 구조 검사는 빈 훅 설정을 정상으로 판단했습니다. 이를 새 실행 코어로 교체하고 있습니다.

## 구조

1. **작은 진입 규칙**: 사용자 범위, 관련 코드 읽기, 결과 검증, 비용 경계만 유지합니다. 도구 기능을 중복 설명하지 않습니다.
2. **작업별 스킬**: 구현·진단, 출처 조사, UI 설계·검증처럼 실제로 서로 다른 절차만 분리합니다. 기본은 자연어 자동 선택입니다.
3. **실행 코어**: 모델과 네트워크에 독립적인 Python 표준 라이브러리로 작업·완료 조건·명령 증거·중단 이유를 저장합니다.
4. **플랫폼 어댑터**: Antigravity의 camelCase 이벤트와 Gemini CLI의 snake_case 이벤트를 개별 파싱합니다. 인증·모델 호출·플랫폼 샌드박스는 호스트가 맡습니다.
5. **패키징**: 하나의 원본에서 플러그인·확장을 생성합니다. 설치 전에 검증하고 이동 기록을 통한 교체와 되돌리기를 제공합니다.
6. **평가**: 실제 명령 종료 코드와 산출물 검사를 수행합니다. 선언된 완료 조건이 적절한지는 별도 리뷰·실험으로 평가합니다.

코드 조회는 네이티브 도구를 우선하고, 필요할 때 상태를 만들지 않는 `inspect` 명령으로 여러 텍스트 파일을 함께 읽습니다. 줄 범위·출력 제한·이어 읽을 위치와 전체 파일 해시의 유효 범위를 구분합니다. 해당 파일을 읽는 중 내용이나 경로가 교체되면 결과를 폐기합니다. 파일 간 원자적 스냅샷은 제공하지 않습니다.

평가 기준은 제품의 private-path 판정이나 프로세스 helper를 import하지 않습니다. 채점 시 표준 라이브러리만 사용하여 제품 구현 변경이 평가 정책까지 바꾸지 않도록 분리했습니다. 설치를 포함한 평가 준비는 별도 단계입니다.

모델 ID를 코어의 분기나 통과 조건으로 사용하지 않습니다. 현재 Gemini 3.8 Flash뿐 아니라 이후 Gemini 모델도 호스트가 선택한 모델 그대로 실행합니다. 미확인 모델의 사고 수준·토큰 한도를 추정하지 않고, 필요한 설정만 공식 메타데이터와 호스트 지원 여부로 확인합니다. Gemini 4 Pro의 향후 사양과 품질은 미검증입니다.

## 모듈 책임

한 모듈이 여러 책임을 갖지 않도록 경계를 여기에 고정합니다. 실제 파일과 이 표가 어긋나면 검사가 실패합니다. 파일별 전체 원문은 [현재 원본 전체](../inventory/current/README.md)에 있습니다.

| 모듈 | 책임 |
| --- | --- |
| `gtg/platforms.py` | 호스트별 훅 이벤트·설치 경로·감지 표식의 단일 정의 |
| `gtg/spec.py` | 작업 계약 검증, 검증 대상의 지문과 범위 예산 |
| `gtg/store.py` | 작업·실행·메모의 SQLite 상태 |
| `gtg/runner.py` | 검증 명령 실행과 현재 상태 조회 |
| `gtg/coverage.py` | 검사가 실제로 실행한 코드 파일 관찰 |
| `gtg/certificate.py` | 완료 증명서 생성과 상태 DB 없는 재실행 |
| `gtg/checkpoints.py` | 검증과 분리된 재개용 메모 |
| `gtg/sessions.py` | 호스트 세션 연결·재개 예산·중단 |
| `gtg/hooks.py` | 호스트 이벤트를 로컬 증거와 연결 |
| `gtg/context_message.py` | 훅 안내의 표현. IO 없음 |
| `gtg/discovery.py` | 읽기 전용 작업 후보 조회 |
| `gtg/inspection.py` | 여러 텍스트 파일의 범위 조회 |
| `gtg/package.py` | 호스트별 패키지 생성과 원문·훅 검증 |
| `gtg/install.py` | 호스트 감지·설치·검사·제거·복구 |
| `gtg/install_journal.py` | 파일 이동의 사전 기록과 되돌리기 |
| `gtg/legacy.py` | 구형 프로필 링크의 보존과 복구 |
| `gtg/__main__.py` | 에이전트가 쓰는 CLI 진입점 |

평가 코드의 경계는 [평가 문서](../../../evals/README.md)에 있습니다. 채점 경로는 제품을 import하지 않습니다.

## 상태와 완료

작업마다 목표·완료 조건·검증 대상 파일·고정된 검증 명령을 정의합니다. 임의의 `echo passed`가 다른 완료 조건을 대신할 수 없습니다. 실행기는 동일 명령을 직접 실행해 종료 코드·시간·검증 당시 파일 해시를 기록합니다.

모든 완료 조건이 현재 파일 상태에 대해 통과해야 완료할 수 있습니다. 검증 후 코드가 바뀌거나 검사 명령이 실패하면 이전 성공은 완료 근거로 쓰지 않습니다. 실행 중 프로세스 중단과 재시작도 완료로 처리하지 않습니다. 작업 간 상태가 섞이지 않게 식별자를 분리합니다.

검증 대상 목록과 검사 명령 자체를 모델이 부적절하게 선택할 수 있다는 한계는 남습니다. 실행 증거는 강제할 수 있지만 사용자의 요구 충족을 자동 증명하지는 않습니다. 이것을 별도 결과 평가가 보완합니다.

같은 세션의 동일 작업 시작은 기존 작업을 반환합니다. 생성과 세션 연결을 하나의 DB 트랜잭션으로 처리하여 중복 요청과 실패 후 고아 작업을 막습니다. 재개용 checkpoint는 별도 이력에 저장하며, 실제 검사 결과를 변경하지 않습니다. 메모에 연결한 파일의 해시가 달라지면 재확인이 필요한 것으로 표시합니다.

새 세션에는 `tasks`가 읽기 전용의 작은 후보 목록을 제공합니다. 목록의 기록된 검사 수는 현재 파일 검증을 의미하지 않습니다. `status`는 전체 원래 명세와 현재 파일 상태를 확인하고 `attach`는 기존 작업 ID를 유지하며 연결만 옮깁니다. 파일을 과거 스냅샷으로 되돌리는 동작은 포함하지 않습니다.

연결 변경은 트랜잭션 안에서 수행합니다. 실행 중인 등록 검사는 변경을 막고, 확인되지 않은 다른 활성 연결은 기본적으로 거부합니다. 호스트 턴 관측인 `turn_open`은 PID 검사나 파일 잠금이 아닙니다. 이전 호스트를 종료시키는 권한이나 기능을 추가하지 않습니다. 예전 DB의 관측 정보는 `null`로 두고 추정하지 않습니다.

## 중단과 비용

사용자 중단·취소·권한 요청·호스트 오류·쿼터 제한은 계속 실행으로 덮지 않습니다. 재시도는 상한과 동일 실패 감지를 갖습니다. 백그라운드 작업이 남아 있으면 완료로 판정하지 않습니다. 모든 훅은 로컬 계산만 수행하며 훅에서 LLM을 호출하지 않습니다.

검증 CLI의 SIGTERM·SIGINT는 자체 검증 프로세스 그룹을 정리하고 중단 상태를 기록합니다. 정상 종료한 부모가 같은 그룹의 하위 프로세스를 남겨도 검증 성공으로 처리하지 않습니다. 이는 POSIX 그룹의 처리이며, 새 세션으로 빠져나간 프로세스나 OS 전체 손상을 격리하는 샌드박스는 아닙니다.

자동 재개 횟수가 소진되면 세션을 일시 중단하고 이유를 저장합니다. 중복 종료 이벤트는 진행 중인 재개를 취소하지 않으며, 활성 상태의 resume 호출은 예산을 다시 채우지 않습니다. 현재 사용자 요청이 명시적으로 재개를 뜻할 때 중단을 해제합니다.

여러 작업공간은 호스트 세션 ID가 같은 로컬 작업을 함께 확인합니다. 미완료 조건을 합치고 일시 중단과 재개 횟수를 공유하며, 작업공간 없는 일반 대화에는 상태 DB를 만들지 않습니다.

설치·제거·복구의 파일 이동은 먼저 디스크에 기록합니다. 미완료 기록은 다음 실행에서 역순으로 되돌립니다. inode가 달라진 사용자 파일을 발견하면 덮어쓰지 않고 복구 기록을 남깁니다. SIGKILL로 종료한 실제 프로세스를 대상으로 검증했으며, 전원 차단·파일시스템 손상까지 검증한 것은 아닙니다.

## 신뢰 경계

외부 자료와 도구 출력은 명령이 아닙니다. 훅은 원본 대화·도구 인수·환경 변수 전체를 저장하지 않습니다. 상태 경로는 검증된 로컬 영역으로 제한하고 심볼릭 링크를 통한 외부 접근을 거부합니다. 자체 정규식 검사를 OS 샌드박스라고 주장하지 않습니다. 네이티브 도구의 승인과 샌드박스를 약화시키지 않습니다.

## 마이그레이션과 절충

먼저 원본 전체 기록과 새 코어 테스트를 만듭니다. 다음으로 별도 시험 경로에 패키지를 생성해 설치·실패·복구를 검사합니다. 이 경로가 검증된 뒤 옛 프로필과 중복 사본을 제거하고 기본 설치 경로를 전환합니다.

Python은 기존 도구와 이어지고 외부 의존성이 없습니다. 매 훅에서 프로세스를 띄우는 비용을 실측했습니다. 소스 300개·테스트 120개 프로젝트에서 중앙 102밀리초이고, 검증 범위 상한 근처에서 재해싱까지 포함해도 1.2초로 5초 제한 안에 있습니다. 문서 계약만으로 실제 호스트의 호출 순서를 보장할 수 없으므로 최종적으로 최소 실환경 확인이 필요합니다.
