# 미실행 목록을 만들지 못한 이유를 밝히기

확인일: 2026-09-09. 실제 모델 요청은 0회입니다. GTG를 이 저장소 자체에 걸어 확인했습니다.

## 어떻게 발견했나

GTG로 이 저장소의 오늘 작업을 등록하고 실제로 검증했습니다.

```
verified: True
  suite: passed  미실행 대상 관찰 못함
  catalog: passed  미실행 대상 관찰 못함
```

두 검사 모두 `coverage_observed=True`(suite는 실행 파일 67개 관측)인데 미실행 목록이 `null`이었습니다. 원인을 찾아보니 검증 범위 `["gtg","tests","evals","scripts"]` 안의 **`scripts/install.sh` 하나** 때문이었습니다. 관찰할 수 없는 언어가 범위에 하나라도 있으면 미실행을 주장하지 않는 설계는 옳지만, **왜인지 알려주지 않아** 모델이 손쓸 방법이 없었습니다.

셸 스크립트 한 개가 있는 저장소는 흔합니다. 이 기능은 조용히 아무 값도 내지 않는 상태로 남아 있었습니다.

## 고침

`executed_watch`가 판단을 막은 파일을 함께 돌려줍니다. 반환값이 `(실행, 미실행, 막은 파일)` 세 개가 됩니다.

- 검사 결과와 `status`에 `unobservable_watch`가 들어갑니다.
- 증명서에 `unobservable_scope`가 들어갑니다. `coverage_complete: false`의 이유입니다. 본문 필드가 늘어 `schema_version`은 3입니다.
- 훅 메시지에는 미실행 목록을 만들지 못한 검사가 있을 때만 최대 3개를 붙입니다.
- 목록이 비어 있으면 이유가 관찰 불가 언어가 아니라 범위 크기(`MAX_WATCHED_FILES`)입니다. 두 원인을 구분합니다.

배포 지시문에도 한 문장을 더해, 검사를 나눠 관찰 가능한 범위만 따로 등록하면 나머지의 미실행 목록을 얻을 수 있다고 알립니다.

## 실제로 통하는지

같은 저장소에서 범위를 관찰 가능한 파일로 좁혀 다시 등록했습니다.

```
상태: passed
막은 파일: []
한 번도 실행되지 않은 검증 대상: 22
```

`null`이던 자리에 실제 목록이 나왔습니다. 대부분 평가용 고정 자료(`evals/fixtures/**`)이며, 시행 폴더로 복사된 뒤에 실행되므로 원본 경로는 실행되지 않습니다.

목록에 `scripts/gtg_runner.py`가 들어 있습니다. 설치본 `run.py`의 원본이자 모든 실호스트 호출의 진입점입니다. 확인해 보니 `test_scenario`·`test_hook_concurrency`·`test_hook_resilience` 등 여러 검사가 **설치된 사본** 경로로 이 파일을 실행합니다. 즉 실제 검증 공백이 아니라, 이 관찰이 내용이 아닌 **파일 경로 단위**라는 한계가 드러난 것입니다. 문서에 이미 적어 둔 성질이며 이번 사례로 실제 모습을 확인했습니다.

## 남은 한계

- 여전히 줄·분기 단위가 아니라 파일 단위 관찰입니다. 같은 내용을 다른 경로에서 실행하면 원본은 미실행으로 나옵니다.
- 막은 파일 목록은 최대 8개 표본입니다. 전체 목록이 아닙니다.
- 셸 스크립트 자체를 관찰하지 않는 결정은 그대로입니다. `BASH_ENV`와 DEBUG 트랩은 `source` 대상과 `/bin/sh`를 놓쳐 부분 관찰이 되고, 부분 관찰은 실행한 파일을 미실행으로 잘못 보고합니다.
