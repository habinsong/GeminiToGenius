# 동작 방식

사용자는 평소처럼 자연어로 요청합니다. 이후 흐름은 모델과 플랫폼 훅이 처리합니다.

```
사용자 요청
   ↓
턴 시작 훅 — 세션 파라미터와 직전 미검증 상태를 모델에 전달
   ↓
모델 판단 — 다단계 작업인 경우 완료 조건과 검증 명령을 등록
   ↓
verify — 등록된 명령을 실제로 실행하고 종료 코드와 파일 해시를 기록
   ↓
턴 종료 훅 — 미검증 상태가 남아 있으면 설정된 예산 내에서 재개
   ↓
certify — 검증 주장과 실행 근거를 단일 증명서 파일로 결합
```

## 완료 조건을 사전에 고정합니다

모델이 요청을 분석한 뒤 `.gtg/task.json`에 검증 명령을 기록합니다. 어떤 조건을 만족해야 작업이 완료된 것인지 미리 정의하는 단계입니다. 한 번 등록된 검증 명령은 사후에 임의로 변경할 수 없습니다. 작업 도중 통과하기 쉬운 명령으로 조건을 낮추는 행위를 방지하기 위함입니다.

세부 명세 구조는 [작업 명세](../reference/task-spec.md) 문서를 참고하세요.

## 검증 명령은 실제 환경에서 직접 실행합니다

`verify`는 등록된 명령을 가감 없이 그대로 실행합니다. 실행 출력은 호스트 인터페이스로 전달하며, 프로세스 종료 코드, 소요 시간, 검사 대상 파일의 SHA-256 해시를 로컬에 기록합니다. 실제로 실행되지 않은 검증을 통과로 처리할 수 없습니다.

이미 통과한 검증이라도 이후 대상 파일이 수정되면 즉시 `stale` 상태로 전환됩니다. 이전 성공 기록을 현재 상태의 근거로 인정하지 않습니다.

## 완료 보고 시 구체적인 실행 근거를 첨부합니다

`certify`는 실행한 명령, 종료 코드, 파일 지문을 단일 문서에 묶어 기록합니다. 검증 결과를 전달받는 측은 별도 데이터베이스 없이 `replay` 명령만으로 결과를 독립 재현할 수 있습니다. 판정 결과는 `pass`, `invalid`, `inconclusive` 세 가지이며, 불확실한 상태를 성공(`pass`)으로 왜곡하지 않습니다.

상세한 규격은 [완료 증명서](../reference/certificate.md) 문서를 참고하세요.

## 검증되지 않은 범위도 투명하게 공개합니다

검증 명령이 실행되는 동안 실제로 어떤 코드 파일이 호출되었는지 런타임을 관찰합니다. 통과한 검증에서 한 번도 실행되지 않은 파일이 있으면 결과 보고에 명시합니다. 관찰을 지원하지 않는 언어 환경이 포함되어 있다면 확인되지 않은 범위를 숨기지 않고, 어떤 런타임 제한 때문에 판단이 불가능했는지 구체적으로 밝힙니다.

상세한 측정 방식과 관측 한계는 [실행 관측](../architecture/coverage.md) 문서를 참고하세요.

## 다중 턴에 걸쳐 작업을 안정적으로 이어갑니다

턴이 끝나는 시점에 미검증 상태가 남아 있다면 훅이 정해진 예산 내에서 자동으로 재개를 요청합니다. 기본값은 2회입니다. 자동 재개는 사용자의 모델 쿼터를 소모하므로 무제한 반복하지 않습니다.

세션 연결이 끊기더라도 등록된 작업 데이터는 유지됩니다. 새 세션에서 `tasks`로 기존 작업을 조회하고 `attach`하면 완료 조건과 검증 이력, 메모를 그대로 이어받습니다. 긴 작업 중간에는 `checkpoint`로 재개용 메모를 남길 수 있습니다. 다만 메모는 진행 상황 기록일 뿐, 검증 명령 성공을 대체하지는 않습니다.

## 중요한 주장과 실사용 조건을 검토합니다

기본 규칙과 개발·조사·UI 스킬은 무엇이든 긍정적으로 보거나 성공을 전제하지 않도록 안내합니다. 사실·추정·제안·미확인을 구분하고, API·숫자·원인·구현 가능성을 원본 근거와 대조합니다. 근거 있는 작은 제안까지 무조건 기각하는 것도 피합니다.

목표 환경과 시험 환경의 OS·장비·데이터 규모·권한·자원 조건을 비교하고 모의 시험의 성공 범위를 제한합니다. `environment`는 로컬 Python 프로세스의 필요조건을 비교하는 보조 명령입니다. 실제 기기 동작이나 제품 적합성은 별도 시험이 필요합니다.

이 지침은 자연어 설명의 진실성을 자동 판정하는 장치가 아닙니다. 평가에는 거짓 API, 부풀린 결과, 무조건적 긍정, 조건상 불가능한 제안, 환경 차이, 범위 확대, 메모의 추정 승격과 정보 부족 사례를 마련했으며, 근거 있는 제안의 채택 사례도 포함합니다. 설명의 정확성은 원본과 실제 응답을 대조하는 사람 검토 대상으로 남깁니다. [평가 절차](../../evals/README.md).

## 작업 등록 조건

코드 동작·타입·호출 관계 변경은 단일 파일이어도 빌드와 필수 시험을 코드 작업 계약에 연결하도록 안내합니다. 문답·문구·포맷만 바꾸는 작업은 관련 검사로 끝냅니다. 조사만·시험만 요청한 작업을 임의 구현으로 확대하지 않습니다.

코드 작업 계약은 실제 빌드가 현재 입력에서 통과하기 전에는 필수 시험 실행을 차단합니다. 빌드·시험 입력과 연결한 PRD가 바뀌면 이전 성공을 무효화하고, 빌드를 재실행했으면 시험도 다시 실행합니다. Python 필수 시험 실행기는 실제 성공한 시험 ID를 확인해 다른 시험의 성공이나 필수 시험 skip으로 누락을 숨기지 않게 합니다. [계약](../reference/task-spec.md).

이전 지침의 실제 호스트 시험에서는 20회 요청 중 5회에서 작업을 등록했습니다. 등록된 5회는 검증을 거쳐 증명서를 생성했으나, 등록하지 않은 단일 수정 작업에서는 GTG 사용 여부에 따른 품질 차이가 없었습니다. 새 지침의 실제 등록률과 모델 품질 개선은 아직 확인하지 않았습니다. 세부 데이터는 [검증 기록](../verification/README.md)에 있습니다.
