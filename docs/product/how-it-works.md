# 동작 방식

자연어로 요청하시면 모델과 플랫폼 훅이 검증 흐름을 수행합니다.

```
사용자 요청
   ↓
턴 시작 훅 -> 세션 파라미터와 직전 미검증 상태를 모델에 전달
   ↓
모델 판단 -> 다단계 작업인 경우 완료 조건과 검증 명령을 등록
   ↓
verify -> 등록된 명령을 실제로 실행하고 종료 코드와 파일 해시를 기록
   ↓
턴 종료 훅 -> 미검증 상태가 남아 있으면 설정된 예산 내에서 재개
   ↓
certify -> 검증 주장과 실행 근거를 단일 증명서 파일로 결합
```

## 완료 조건의 사전 고정

모델은 요청을 분석한 뒤 `.gtg/task.json`에 검증 명령을 기록해 작업의 완료 조건을 미리 정합니다. 등록한 검증 명령은 나중에 바꿀 수 없으므로 작업 도중 통과하기 쉬운 것으로 조건을 낮추는 일을 차단합니다.

세부 명세 구조는 [작업 명세](../reference/task-spec.md) 문서를 참고해 주십시오.

## 실제 환경에서의 검증 실행

`verify`는 등록된 명령을 있는 그대로 실행하고 프로세스 종료 코드와 소요 시간, 검사 대상 파일의 SHA-256 해시를 로컬에 기록합니다. 통과 처리는 실제 실행 결과가 있을 때만 이루어집니다.

이미 통과한 검증이라도 이후 대상 파일이 수정되면 즉시 `stale` 상태로 바뀌며 이전 성공 기록은 현재 상태의 근거에서 빠집니다.

## 구체적 실행 근거 첨부

`certify`는 실행한 명령과 프로세스 종료 코드, 파일 지문을 증명서 하나에 기록합니다. 이 증명서를 받은 제3자는 별도의 외부 데이터베이스 없이 `replay` 명령만으로 전체 검증 과정을 다시 실행해 확인할 수 있습니다. 판정 결과는 `pass`, `invalid`, `inconclusive` 세 가지이며 불확실한 상태는 `inconclusive`로 판정하고 `pass`로 처리하지 않습니다.

상세 규격은 [완료 증명서](../reference/certificate.md) 문서를 참고해 주십시오.

## 미검증 범위의 공개

검증 명령이 실행되는 동안 호출된 코드 파일을 관찰하며 통과한 검증에서 실행되지 않은 파일이 있으면 결과 보고에 명시합니다. 관찰을 지원하지 않는 언어 환경은 런타임 제약을 이유로 판단 불가라고 밝힙니다.

측정 방식과 관측 한계는 [실행 관측](../architecture/coverage.md) 문서를 참고해 주십시오.

## 다중 턴 작업 연계

턴 종료 시점에 미검증 상태가 남아 있으면 훅이 정해진 예산 안에서 재개를 요청합니다. 예산의 기본값은 2회이며 이 상한으로 모델 쿼터 소모를 막습니다.

세션이 끊겨도 등록된 작업 데이터는 유지됩니다. 새 세션에서 `tasks`로 기존 작업을 조회하고 `attach`하면 완료 조건과 검증 이력을 이어받습니다. 긴 작업 중간에는 `checkpoint`로 재개용 메모를 남기실 수 있으나, 메모는 기록일 뿐이라 검증 명령의 실제 성공을 대신할 수 없습니다.

## 주장과 실사용 조건 검토

기본 규칙과 스킬은 성공을 전제하지 않도록 안내하고, 사실과 추정, 제안, 미확인을 구분해 쓰며 API와 수치를 원본 근거와 대조하라고 요구합니다.

작업 완료 전 핵심 주장마다 반박 증거를 먼저 정의하고, 파일을 다시 열어 명령을 실행하거나 출처를 확인하도록 이끕니다. 버전이 걸린 API나 새로운 오류는 웹에서 원문을 직접 열어 확인하며 근거로 삼는 것은 원문뿐입니다.

`environment`는 로컬 Python 프로세스의 필요조건을 비교하는 보조 명령이며, 실제 기기 동작이나 상용 환경 적합성은 별도 시험이 필요합니다. 상세 절차는 [평가 절차](../../evals/README.md)에 기술되어 있습니다.

## 코드와 문서 검사

결과물을 직접 읽는 검사를 운영합니다.

`structure`는 변경된 코드에서 빈 함수, TODO, 대형 파일 누적을 찾아 차단하며 사용처가 없는 정의를 알립니다. 작업 명세에 등록하면 이 검사를 통과해야 작업이 끝납니다.

문서의 문체는 `ai-smell-polish` 스킬의 `ai-smell`이 측정합니다. `analyze`가 점수를 내고, `polish`가 뜻이 바뀌지 않는 항목만 고치며, `verify`가 수치와 인용 보존 여부와 변경률을 대조합니다. 점수는 AI 판별 확률이 아니며 휴리스틱 기준입니다. 작업 명세에는 `analyze --fail-above`를 검사로 등록할 수 있습니다. 상세 내용은 [`vendor/ai-smell-meter`](../../vendor/ai-smell-meter/README.md)를 참고해 주십시오.

## 교훈 기록

검증에서 실수가 확인되면 해당 저장소에서 유효한 사실을 근거 파일과 함께 `lesson`으로 기록합니다. 다음 세션 턴 안내에 최근 교훈이 전달되어 동일 실수를 줄입니다. 근거 파일이 작업 공간에 없으면 저장하지 않으며 최대 100개까지 관리합니다.

## 작업 등록 조건

코드 동작이나 타입을 바꾸는 작업은 빌드와 필수 시험을 코드 작업 명세에 연결해 두어야 합니다. 단순 문답이나 서식 수정은 관련 검사만 확인하면 됩니다.

코드 작업 명세에서는 빌드가 통과하기 전까지 필수 시험을 실행할 수 없습니다. 입력이 바뀌면 이전 성공 기록이 무효가 되고, 빌드를 다시 실행하면 필수 시험도 이어서 다시 실행됩니다. 필수 시험 실행기는 통과한 항목의 식별자를 직접 확인하므로 일부를 빠뜨리고 통과할 수 없습니다. 상세 내용은 [작업 명세](../reference/task-spec.md) 문서를 참고해 주십시오.
