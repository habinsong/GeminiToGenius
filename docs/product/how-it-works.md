# 동작 방식

평소처럼 자연어로 요청하시면 됩니다. 이후의 세부 흐름은 모델과 플랫폼 훅이 순서대로 처리합니다.

```
사용자 요청
   ↓
턴 시작 훅 — 세션 파라미터와 직전 미검증 상태를 모델에 전달
   ↓
모델 판단 — 다단계 작업인 경우 완료 조건과 검증 명령을 등록
   ↓
verify — 등록된 명령을 실제로 실행하고 종료 코드와 파일 해시를 기록
   ↓
턴 종료 훅 — 미검증 상태가 남아 있으면 설정된 예산 내에서 재개
   ↓
certify — 검증 주장과 실행 근거를 단일 증명서 파일로 결합
```

## 완료 조건을 사전에 고정합니다

모델이 요청을 분석한 뒤 `.gtg/task.json`에 검증 명령을 기록합니다. 어떤 조건을 만족해야 작업이 완료된 것인지 미리 정의하는 단계입니다. 한 번 등록된 검증 명령은 사후에 임의로 변경할 수 없습니다. 작업 도중 통과하기 쉬운 명령으로 조건을 임의로 낮추는 행위를 방지하기 위함입니다.

세부 명세 구조는 [작업 명세](../reference/task-spec.md) 문서를 참고해 주십시오.

## 검증 명령은 실제 환경에서 직접 실행합니다

`verify`는 등록된 명령을 가감 없이 그대로 실행합니다. 실행 출력은 호스트 인터페이스로 전달하며 프로세스 종료 코드와 소요 시간, 검사 대상 파일의 SHA-256 해시를 로컬에 기록합니다. 실제로 실행되지 않은 검증을 통과로 처리할 수는 없습니다.

이미 통과한 검증이라도 이후 대상 파일이 수정되면 즉시 `stale` 상태로 전환됩니다. 이전 성공 기록을 현재 상태의 근거로 인정하지 않습니다.

## 완료 보고 시 구체적인 실행 근거를 첨부합니다

`certify`는 실행한 명령과 종료 코드, 파일 지문을 단일 문서에 묶어 기록합니다. 검증 결과를 전달받는 측은 별도 데이터베이스 없이 `replay` 명령만으로 결과를 독립적으로 재현할 수 있습니다. 판정 결과는 `pass`, `invalid`, `inconclusive` 세 가지이며, 불확실한 상태를 성공(`pass`)으로 왜곡하지 않습니다.

상세한 규격은 [완료 증명서](../reference/certificate.md) 문서를 참고해 주십시오.

## 검증되지 않은 범위도 투명하게 공개합니다

검증 명령이 실행되는 동안 실제로 어떤 코드 파일이 호출되었는지 런타임을 관찰합니다. 통과한 검증에서 한 번도 실행되지 않은 파일이 있으면 결과 보고에 명확히 밝힙니다. 관찰을 지원하지 않는 언어 환경이 포함되어 있다면 확인되지 않은 범위를 숨기지 않고, 어떤 런타임 제약 때문에 판단이 불가능했는지 구체적으로 설명해 드립니다.

상세한 측정 방식과 관측 한계는 [실행 관측](../architecture/coverage.md) 문서를 참고해 주십시오.

## 다중 턴에 걸쳐 작업을 안정적으로 이어갑니다

턴이 끝나는 시점에 미검증 상태가 남아 있다면 훅이 정해진 예산 내에서 재개를 요청합니다. 기본값은 2회입니다. 재개 요청은 사용자의 모델 쿼터를 소모하므로 무제한 반복하지 않습니다.

세션 연결이 끊기더라도 등록된 작업 데이터는 안전하게 유지됩니다. 새 세션에서 `tasks`로 기존 작업을 조회하고 `attach`하면 완료 조건과 검증 이력, 메모를 그대로 이어받습니다. 긴 작업 중간에는 `checkpoint`로 재개용 메모를 남기실 수 있습니다. 다만 메모는 진행 상황 기록일 뿐이며 검증 명령의 실제 성공을 대신하지는 않습니다.

## 중요한 주장과 실사용 조건을 검토합니다

기본 규칙과 개발·조사·글쓰기·UI 스킬은 무엇이든 맹목적으로 긍정하거나 성공을 전제하지 않도록 안내합니다. 사실과 추정, 제안, 미확인을 엄격히 구분하고, API와 수치, 원인, 구현 가능성을 원본 근거와 대조하되 합리적인 근거가 있는 제안까지 무조건 기각하지는 않습니다.

3.1의 규칙은 작업을 끝내기 전에 핵심 주장마다 "틀렸다면 무엇이 보여야 하는가"를 먼저 정하고, 초안을 다시 읽는 대신 파일을 다시 열고 명령을 다시 돌리며 다른 출처를 찾아 스스로 반박해 보도록 유도합니다. 자기 답만 다시 읽는 방식의 자기 수정은 추론 과제에서 효과가 없거나 오히려 품질이 떨어졌다는 연구가 있고, 검색이나 코드 실행 같은 외부 도구로 직접 확인할 때 오류가 실질적으로 교정되었다는 연구 결과가 있기 때문입니다. 버전이 걸린 API나 처음 보는 오류, 학습 시점 이후의 사실은 웹에서 원문을 직접 열어 확인하도록 이끌며, 검색 도구가 돌려주는 요약 문장은 근거로 인정하지 않습니다.

목표 환경과 시험 환경의 OS·장비·데이터 규모·권한·자원 조건을 비교하고 모의 시험의 성공 범위를 제한합니다. `environment`는 로컬 Python 프로세스의 필요조건을 비교하는 보조 명령입니다. 실제 기기 동작이나 상용 환경 적합성은 별도의 독립적인 시험이 필요합니다.

이 지침이 자연어 설명의 진실성을 기계적으로 판정해 주는 장치는 아닙니다. 평가에는 존재하지 않는 API 호출, 부풀려진 결과, 무조건적인 긍정, 조건상 불가능한 제안, 환경 차이, 범위 확대, 메모의 추정 승격과 정보 부족 사례를 마련해 두었으며, 근거 있는 제안을 정당하게 채택하는 사례도 포함했습니다. 설명의 정확성은 원본과 실제 응답을 대조하는 사람의 검토 대상으로 남겨 둡니다. 상세 내용은 [평가 절차](../../evals/README.md)에 기술되어 있습니다.

## 코드와 글도 검사로 확인합니다

모델이 "TODO를 지웠습니다"라거나 "상투구를 걷어냈습니다"라고 말하는 것만으로는 충분한 근거가 되지 못합니다. 실제로 Gemini 3.8 Flash가 지시받은 금지 형식을 "모두 없앴습니다"라고 답한 바로 다음 줄에서 그 형식을 다시 쓴 사례가 보고되기도 했습니다. 그래서 3.1부터는 결과물을 직접 읽는 검사 두 가지를 운영합니다.

`structure`는 이번에 변경된 코드에서 본문이 빈 함수나 새 TODO, 큰 파일에 누적된 기능, 메서드가 계속 늘어나는 클래스를 찾아 차단하며, 구현이 하나뿐인 추상화나 인자만 넘기는 래퍼, 부르는 곳이 없는 새 정의는 검토 대상으로 알립니다. `prose`는 문서에서 지워도 뜻이 훼손되지 않는 상투구를 차단하고, 번역투 표현이 한 문단에 몰리거나 짧은 문장이 뚝뚝 끊기는 곳을 줄 번호와 함께 찾아 드립니다. 두 검사 모두 작업 계약에 등록하면 다른 시험과 마찬가지로 온전히 통과해야 작업이 완료됩니다.

3.2부터 `prose`는 글의 갈래(`--register`)를 지정받습니다. 같은 표현이라도 논문에서는 관례이고 기술 문서에서는 흐린 문장이 될 수 있으므로 갈래마다 규칙을 끄고 완화하며 보강하고, 찾은 표현의 빈도를 글 분량으로 나눈 0~100점 점수와 A~D 등급으로 환산합니다. 3.3부터는 파일로 저장하지 않은 글도 표준 입력(`-`)이나 `--text`로 검사할 수 있으며, 윤문한 글은 `--original`로 원문과 대조하여 수치와 인용구, URL, 코드가 보존되었는지와 단어 수정 비율을 계산합니다. 문서 전체 및 문단 안 횟수 기준은 글 분량에 비례하여 유연하게 계산되므로(차단 규칙 제외), 긴 문서가 단순히 분량이 많다는 이유만으로 경고를 쏟아내지 않습니다. 점수는 AI가 썼을 확률이 아니며, 규칙 목록에 없는 문체 버릇은 점수에 반영되지 않습니다. 이론적 근거와 한계는 [3.3.0 검증 기록](../verification/3.3.0.md)에 정리되어 있습니다.

두 검사 모두 표현 목록과 코드 형태를 바탕으로 확인하는 경험적 규칙(휴리스틱)입니다. 검사를 통과했다고 해서 소프트웨어 아키텍처나 문장의 품격이 보장되는 것은 아니며, 내용의 사실 여부까지 판별해 주지는 않습니다. 상세한 내용은 [명령 목록](../reference/cli.md#결과물-검사)을 참고해 주십시오.

## 실수를 다음 세션에 남깁니다

검증 과정에서 실수가 드러나면 모델은 "sdk.py에는 export_rows가 없고 실제 함수는 write_rows다"처럼 해당 저장소에서만 유효한 사실을 근거 파일과 함께 `lesson`으로 남깁니다. 다음 세션의 첫 턴 안내에 최근 교훈 다섯 개가 기록 데이터로 전달되므로, 동일한 함수를 다시 꾸며낼 가능성을 낮추기 위한 장치입니다. 근거 파일이 작업 공간에 없거나 근거가 전혀 없으면 저장하지 않으며, 중복된 문장은 한 번만 저장하고 오래된 기록부터 정리하여 100개를 넘지 않도록 관리합니다. 교훈 기록이 실제로 반복 실수를 얼마나 줄여 주는지는 아직 정량 측정하지 않았습니다.

## 작업 등록 조건

코드 동작이나 타입, 호출 관계를 바꾸는 작업은 파일 하나만 수정하더라도 빌드와 필수 시험을 코드 작업 계약에 연결하도록 안내합니다. 문답이나 문구, 서식만 수정하는 작업은 관련 검사만 확인하고 마무리합니다. 조사나 시험만 요청받은 작업을 임의로 구현 단계까지 확대하지 않습니다.

코드 작업 계약은 실제 빌드가 현재 입력 상태에서 통과하기 전까지는 필수 시험의 실행을 차단합니다. 빌드나 시험 입력에 연결된 PRD가 바뀌면 이전 성공 기록을 무효화하며, 빌드를 다시 실행했으면 시험도 다시 수행합니다. Python 필수 시험 실행기는 실제로 통과한 시험 식별자를 직접 확인하여, 다른 시험의 성공이나 필수 시험 skip으로 누락을 가리는 행위를 원천 방지합니다. 상세 내용은 [계약](../reference/task-spec.md) 문서를 참고해 주십시오.

이전 지침을 적용한 실제 호스트 시험에서는 20회 요청 가운데 5회에서 작업을 등록했는데, 등록된 5회는 엄격한 검증을 거쳐 완료 증명서를 발급했으나 작업을 등록하지 않은 단순 단일 수정에서는 GTG 사용 여부에 따른 품질 차이가 뚜렷하지 않았습니다. 아울러 Gemini가 사용자 스킬을 스스로 잘 열지 않는다는 보고가 있었으므로, 3.1은 핵심 행동 지침을 스킬이 아닌 상시 규칙과 턴 시작 안내에 배치하고 실행기 경로도 안내 문구에 직접 포함해 두었습니다. 새 지침의 실제 등록률과 모델 품질 개선 효과는 아직 실측하지 못했으며 구체적인 데이터는 [검증 기록](../verification/README.md)에서 확인하실 수 있습니다.
