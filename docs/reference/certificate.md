# 완료 증명서

작업 완료를 보고할 때 주장과 검증 근거를 단일 파일에 결합합니다. 외부 상태 데이터베이스 없이 이 파일만으로 결과를 독립적으로 다시 확인할 수 있습니다.

```bash
python3 "$GTG" certify TASK_ID --output .gtg/certificate.json
python3 "$GTG" replay --certificate .gtg/certificate.json --workspace .
```

## 증명서 구성 요소

각 완료 조건마다 실제로 실행한 명령과 종료 코드, 검증 대상 파일의 SHA-256 지문을 기록합니다. 성공하지 못한 검사에는 지문을 첨부하지 않으며, 미검증 상태인 작업을 `certify`하면 종료 코드 1과 함께 `verified: false`를 돌려줍니다.

증명서는 본문 전체의 무결성 `digest`를 함께 기록하므로, 내용이 변조되면 `replay`가 실행을 거부합니다.

`code_contract`를 쓰는 작업의 검사는 `depends_on`과 연결된 PRD 요구사항도 함께 기록하고, 이 내용도 digest의 대상이 됩니다.

## `replay` 판정 체계

`replay`의 입력은 증명서와 현재 파일 상태뿐입니다. 명령을 다시 실행했을 때 종료 코드가 0이고 파일 지문도 기록과 모두 같을 때만 `reconstructed: true`로 판정합니다.

| 판정 | 종료 코드 | 설명 |
|---|---|---|
| `pass` | 0 | 모든 검증 명령이 다시 실행되어 성공했고 검사 범위도 완전합니다. |
| `invalid` | 1 | 다시 실행한 검증이 실패했습니다. 증명서가 현재 작업공간 상태를 뒷받침하지 못합니다. |
| `inconclusive` | 2 | 명령은 같은 결과로 다시 실행됐으나 관측할 수 없는 파일 등 때문에 미확인 범위가 남았습니다. |

`inconclusive`는 성공(`pass`)과 별개의 판정입니다. 파일 내용이 바뀌어 같은 결과를 얻지 못하면 `reason: "fingerprint"` 사유를 기록합니다.

증명서에 기록된 원래 작업공간과 다른 디렉터리에서 실행할 때는 명령 내용을 확인한 뒤 `--trust-commands` 플래그를 전달해야 합니다.

## 미검증 스코프

증명서에는 검증의 사각지대를 밝히는 필드가 포함됩니다.

- `unverified_scope`: 통과한 검사가 존재함에도 어떤 검사에서도 호출되지 않은 대상 파일 목록입니다.
- `coverage_complete`: `false`이면 위 목록은 최소 하한선이므로, 비어 있어도 전체 검증이 끝났다고 볼 수 없습니다.
- `unobservable_scope`: 런타임을 추적할 수 없는 파일 목록입니다. 셸 스크립트나 Go, Rust 등이 있으면 이 목록에 들어갑니다.

관측 가능한 런타임과 제한 사항은 [실행 관측](../architecture/coverage.md) 문서를 참고해 주십시오.

## 증명서의 한계

이 증명서는 등록된 검사 범위 안에서 같은 결과를 다시 얻을 수 있다는 것만 증명합니다. 등록된 검사가 사용자의 요구사항을 완전히 포괄하는지는 증명 대상이 아니므로 완료 보고서에는 판정 결과를 있는 그대로 명시해야 합니다.

검사 도중 입력을 고쳐 원래 지문으로 되돌린 정황이 발견되면 `changed_during_check`로 실패 처리하고, 타임아웃이나 중단 시에는 프로세스 그룹을 종료합니다.
