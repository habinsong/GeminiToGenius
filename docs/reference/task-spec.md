# 작업 명세

작업공간 내 `.gtg/task.json` 파일에 정의합니다. 모델이 현재 요청을 분석하여 자동으로 작성하므로 사용자가 직접 편집할 필요는 없습니다.

```json
{
  "schema_version": 1,
  "goal": "현재 요청을 검증 가능한 결과로 적습니다.",
  "max_resumes": 2,
  "checks": [
    {
      "id": "regression",
      "criterion": "수정한 실패 경로가 해결되고 기존 동작이 유지됩니다.",
      "argv": ["python3", "-m", "unittest", "discover", "-s", "tests"],
      "watch": ["src", "tests"],
      "timeout_seconds": 120
    }
  ]
}
```

## 스키마 필드

| 필드 | 설명 |
|---|---|
| `goal` | 이 작업이 완료되었다고 판단할 수 있는 최종 목표 상태를 기술합니다. |
| `checks[].id` | 단일 작업 내에서 고유하게 식별되는 검증 명칭입니다. |
| `checks[].criterion` | 해당 검증이 보증하는 동작 불변식을 자연어로 서술합니다. |
| `checks[].argv` | 실행할 실제 CLI 명령 배열입니다. 셸을 거치지 않고 직접 서브프로세스로 실행합니다. |
| `checks[].watch` | 변경 시 기존 검증 결과를 무효화(`stale`)해야 하는 소스, 테스트, 설정 디렉터리 경로입니다. |
| `checks[].timeout_seconds` | 명령 실행 제한 시간(초)입니다. 기본값은 120초입니다. |
| `max_resumes` | 미검증 시 자연 종료를 되돌려 세션을 재개하는 최대 횟수입니다. 기본값은 2회, 최대 상한은 8회입니다. |

## 등록 거부 대상

`true`, `:`, `echo`, `printf`, `yes`, `sleep`, `cat` 같은 명령은 검증 명령으로 등록할 수 없습니다. 어떠한 환경에서도 항상 성공하거나 입력을 그대로 출력할 뿐이어서 실질적인 코드 동작을 전혀 검증하지 못하기 때문입니다. 셸 파이프라인을 통한 우회 시도까지 사전에 완전 차단하기는 어려우므로, 최종 신뢰성은 [완료 증명서](certificate.md)의 독립 재현(`replay`)을 통해 담보합니다.

심볼릭 링크나 비밀 키·환경 변수 파일 등 민감한 경로는 감시 대상에 포함할 수 없습니다.

## `watch` 감시 범위 상한

**단일 작업의 전체 `watch` 감시 범위는 총 파일 수 20,000개, 총 크기 200MB 이하여야 합니다.** 개별 검사가 아닌 작업 전체가 공유하는 자원 예산이며, 중복된 경로는 1회만 계산합니다. 이 상한을 초과하면 `start` 단계에서 등록을 거부합니다.

플랫폼 훅이 매 턴마다 이 범위의 파일 해시를 대조하므로 성능 보호를 위해 설정된 제한입니다. 실측 시험에서 19,000개 파일 범위를 3개 검사가 감시할 때 훅 왕복 지연이 약 3.4초까지 증가했습니다. 호스트가 부여하는 훅 실행 시간 한도가 5초이므로 여유가 크지 않습니다.

`node_modules`, `target`, `build` 같은 대형 의존성이나 빌드 산출물 폴더를 제외하고 실제 소스 코드와 테스트 디렉터리만 지정하면 이 한도를 넘지 않습니다. `.gtg` 내부 상태 파일과 Python 캐시 디렉터리는 해시 계산 대상에서 자동으로 제외됩니다.

## 등록 후 파일 수정 시 동작

이미 통과한 검증이라도 `watch` 범위 내 파일이 수정되면 해당 결과는 즉시 `stale` 상태로 전환됩니다. 과거의 성공 기록이 현재 작업공간의 무결성을 보장하지 못하기 때문입니다. 변경 후에는 다시 `verify`를 실행하여 검증을 통과해야 합니다.
