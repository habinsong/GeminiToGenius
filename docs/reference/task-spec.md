# 작업 명세

작업공간 내 `.gtg/task.json` 파일에 정의합니다. 모델이 요청을 분석하여 직접 작성하므로 사용자가 직접 편집할 필요는 없습니다.

```json
{
  "schema_version": 1,
  "goal": "현재 요청을 검증 가능한 결과로 작성합니다.",
  "max_resumes": 2,
  "checks": [
    {
      "id": "regression",
      "criterion": "수정한 실패 경로가 해결되고 기존 동작이 유지됩니다.",
      "argv": ["python3", "-m", "unittest", "discover", "-s", "tests"],
      "watch": ["src", "tests"],
      "timeout_seconds": 120
    }
  ]
}
```

## 스키마 필드

| 필드 | 설명 |
|---|---|
| `goal` | 작업 완료를 판단하는 최종 목표 상태를 기술합니다. |
| `checks[].id` | 작업 내에서 고유하게 식별되는 검증 명칭입니다. |
| `checks[].criterion` | 해당 검증이 보증하는 동작 불변식을 기술합니다. |
| `checks[].argv` | 실행할 실제 CLI 명령 배열입니다. 셸을 거치지 않고 서브프로세스로 직접 실행합니다. |
| `checks[].watch` | 변경 시 기존 결과를 무효화(`stale`)하는 소스 및 설정 경로 목록입니다. |
| `checks[].timeout_seconds` | 명령 실행 제한 시간(초)이며 기본값은 120초입니다. |
| `max_resumes` | 미검증 시 세션을 재개하는 최대 횟수이며 기본값은 2회, 최대 8회입니다. |
| `code_contract` | 빌드, 필수 시험, PRD 요구사항을 연결하는 선택 스키마입니다. |

## 코드 작업 완료 조건

`checks`에 빌드와 필수 시험 명령을 정의하고 `code_contract.build_check`에 빌드 검사 ID, `test_checks`에 시험 검사 ID 목록을 지정합니다. 동일한 ID 연결은 거부합니다. 빌드는 시험보다 먼저 나열하십시오.

`requirements`에는 `{"id": "UT-01", "source": "PRD.md", "checks": ["unit"]}` 형식으로 원본 요구사항과 검사 ID를 연결합니다.

계약 사용 시 등록 후 현재 빌드가 성공하기 전까지 필수 시험은 `blocked` 상태가 되어 실행되지 않으며, 빌드를 다시 실행한 뒤에는 이전 시험 성공이 무효화되어 재실행이 필수입니다.

## 등록 거부 대상

`true`, `:`, `echo`, `printf`, `yes`, `sleep`, `cat` 같은 단순 명령은 검증 명령으로 등록할 수 없습니다. 코드 동작을 실제로 검증하지 못하기 때문입니다.

심볼릭 링크나 비밀 키, 환경 변수 파일 등 민감한 경로는 감시 대상에 포함할 수 없습니다.

## `watch` 감시 범위 상한

단일 작업의 전체 `watch` 감시 범위는 총 파일 수 20,000개 및 총 크기 200MB가 상한이며, 이는 작업 전체가 공유하는 자원 예산입니다. 상한을 넘으면 `start` 단계에서 등록을 거부합니다.

플랫폼 훅이 매 턴마다 파일 해시를 대조하므로 성능 보호를 위해 설정된 제한입니다. 대형 산출물 폴더(`node_modules`, `build` 등)를 제외하고 실제 소스 코드와 테스트 디렉터리만 지정하십시오.

## 등록 후 파일 수정 시 동작

이미 통과한 검증이라도 `watch` 범위 내 파일이 수정되면 해당 결과는 즉시 `stale` 상태로 전환됩니다. 과거 성공 기록이 현재 상태를 보장하지 못하므로 다시 `verify`를 실행하여 통과시키십시오.
