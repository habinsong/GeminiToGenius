# 자연어 작업 평가

실제 모델이 요청을 이해하고 처리하는 능력은 단위 테스트로 입증할 수 없습니다. 이 사례는 후속 최소 실환경 검증과 통제된 비교의 입력입니다. 현재 결과를 통과로 채우지 않습니다.

## 독립적인 산출물 검사

작업 폴더의 테스트와 별개인 기준을 사용합니다. 평가 기준·보고서는 에이전트의 작업 폴더 밖에 놓고, 대상 코드는 별도 프로세스에서 실행합니다. 현재 진단 사례는 범위 제한 함수의 오류, 레코드 병합, 수정 금지 요청, 사용자 변경이 있는 CSV 기능 추가와 부분 완료 작업의 재개입니다. 짧은 요청에 필요한 API 계약은 작업 폴더의 README에 제공합니다.

```bash
python3 -m evals.harness prepare bounds /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`prepare`는 새 작업 폴더와 프롬프트를 만들며 모델을 호출하지 않습니다. `--profile baseline`은 GTG를 추가하지 않은 폴더, `--profile gtg`는 프로젝트 플러그인을 설치한 폴더입니다. 실제 호스트가 상속하는 전역 설정은 별도로 기록해야 하므로 이 라벨만으로 순수 기본 환경이라고 주장하지 않습니다.

`--arm`과 `--model`은 비교 보고서에서 결과를 묶는 사용자 선언 라벨입니다. 어떤 하네스와 모델이 실제로 실행됐는지 이 도구가 확인하지는 않습니다.

이후 에이전트에 반환된 `workspace`와 `prompt`를 전달합니다. 실제 실행은 아주 드문 통합 확인에만 사용하며 이 도구는 자동으로 호출하지 않습니다. `grade`는 산출물을 검사하고 매번 별도 JSON 보고서를 남깁니다. 실패 기록을 덮어쓰지 않습니다.

검사는 반환값·예외·입력 보존·기존 호출자·보호 파일을 확인합니다. 작업 폴더의 테스트를 무력화하거나 검사 전에 정상 종료해도 성공 증거로 삼지 않습니다. 평가 정의가 바뀌면 기존 결과와 합치지 않습니다. 수정 금지 사례는 변경 범위만 기계적으로 확인하고 원인 설명의 정확성은 사람의 검토 대상으로 남깁니다.

준비된 요청은 별도 파일과 해시로 기록하고 변경되면 같은 시험으로 채점하지 않습니다. 이는 준비한 요청의 동일성 검사이며 실제 호스트에 어떤 요청을 보냈는지는 별도 실행 기록이 필요합니다. 채점 전후 파일이 달라지면 성공을 인정하지 않습니다. 검증 중 후보를 편집하지 마세요. 두 시점 비교는 파일시스템 전체의 원자적 잠금이나 악성 코드 격리가 아닙니다.

채점 경로는 평가 대상 `gtg` 코드를 import하지 않고 표준 라이브러리만 사용합니다. 반환값은 JSON의 불리언과 숫자를 구분하되, 같은 수를 나타내는 정수·실수와 객체 키 순서 같은 유효한 차이는 허용합니다. 이전에 보존한 실제 평가 묶음은 당시의 평가 코드로 재현하며 새 기준으로 조용히 바꾸지 않습니다.

후보 실행은 명시적인 격리·UTF-8·바이트코드 쓰기 금지 인자를 사용하고, 매 검사 그룹마다 빈 캐시 경로에서 시작합니다. 기존 `.pyc`와 소스의 크기·수정 시각이 같아도 오래된 정상 코드를 현재 소스로 오인하지 않습니다. [Python 실행 옵션](https://docs.python.org/3/using/cmdline.html).

준비·채점의 Python 버전, 운영체제, 아키텍처, 호스트 논리 CPU 수와 검사 시간 제한을 기록합니다. CPU·메모리 한도와 OS 샌드박스를 적용하지 않았다는 사실도 명시합니다. 이 값은 Gemini 실행 호스트의 모델·쿼터·샌드박스 관측을 대신하지 않습니다.

## 사용자 변경이 있는 기능 추가

```bash
python3 -m evals.harness prepare report-export /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`report-export`는 새 임시 Git 저장소에 원본을 인덱스로 등록한 뒤 `app.py`의 파일명을 수정합니다. 커밋은 만들지 않으며 기존 사용자 저장소의 인덱스를 변경하지 않습니다. 후보에는 실제 `git diff`로 보이는 기존 수정이 있습니다.

CSV의 쉼표·따옴표·줄바꿈·빈 입력과 기존 JSON 출력, 공개 호출자의 연결·키워드 인자, 사용자 파일명 보존을 검사합니다. CSV 함수만 만들고 호출자를 연결하지 않으면 실패합니다. 허용된 테스트 파일과 무관한 새 파일을 구분하며 Git 인덱스의 등록 내용과 HEAD의 커밋 ID도 보존해야 합니다. 단순한 Git 상태 조회에 따른 인덱스 캐시 갱신은 변경으로 간주하지 않습니다.

CSV는 셀 값과 행 순서·CRLF 레코드 구분을 비교합니다. 필요한 필드만 인용하거나 모든 필드를 인용하는 유효한 차이를 실패시키지 않습니다. JSON 등 다른 반환값에 이 정규화를 적용하지 않습니다. 위치 인자와 키워드 인자를 모두 호출할 수 있으며 입력 보존도 함께 검사합니다.

기본 프로필과 GTG 프로필에 참조 수정을 적용해 새 사례의 기준 자체를 검사했습니다. [모델 없는 참조 검증](../docs/rebuild/validation/2026-09-08-evaluation/README.md)이며 모델 성공률이나 두 프로필의 성능 비교가 아닙니다. 이 공개 사례에 맞춰 스킬을 조정하지 않았습니다.

## 부분 완료 작업 이어가기

`resume-export`는 CSV 직렬화가 끝났지만 공개 다운로드 연결이 남은 입력입니다. 요청은 짧은 자연어이며 슬래시나 작업 ID를 포함하지 않습니다. 결과 기준은 `report-export`의 함수 검사를 재사용하고 입력·진행 조건은 별도로 기록합니다.

```bash
python3 -m evals.harness prepare resume-export /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

GTG 준비 단계는 이전 작업의 완료된 검사를 실제로 실행하고 메모·중단 상태를 생성합니다. 이 상태는 시험 입력이며 이전에 모델이 수행한 작업이라고 집계하지 않습니다. 더 최근에 완료된 별도 작업도 두어 가장 최근 ID만 선택하는 것과 미완료 목표를 찾는 것을 구분합니다. 기본 프로필에는 같은 코드·진행 문서를 제공하지만 GTG 설치·상태는 만들지 않습니다.

산출물 채점과 기존 작업 연결 여부는 별개입니다. 실제 모델 시험에서는 현재 세션이 원래 작업 ID에 연결됐는지, 목표·기존 검증·메모·사용자 수정이 유지됐는지도 확인해야 합니다.

[실제 새 세션 시험](../docs/rebuild/validation/2026-09-08-resume-eval/README.md)에서 원래 작업 선택·연결과 독립 산출물 8개 검사가 통과했습니다. 사전 이력은 준비 코드가 생성했으며 단일 모델·전역 설정을 상속한 시험입니다. 장기 작업이나 경쟁 비교 결과는 아닙니다.

## 유지보수 경계

| 파일 | 책임 |
| --- | --- |
| `harness.py` | CLI와 기존 Python 진입점 |
| `definitions.py` | 사례·공통 결과 기준·전체 평가 코드 해시 |
| `workspace.py` | 파일·Git 상태와 실행 환경 |
| `preparation.py` | 새 입력 폴더 준비와 단계 조합 |
| `progress.py` | 실제 검사로 부분 완료 상태 생성 |
| `grading.py` | 독립 프로세스 결과·산출물·변경 범위 채점 |
| `probe.py` | 후보 함수 호출을 별도 프로세스에서 수행 |

준비 과정에서만 제품 코드를 사용할 수 있습니다. 채점 경로는 제품을 import하지 않습니다. 분리된 모든 평가 모듈과 fixture를 정의 해시에 포함해 구현이 바뀐 결과를 섞지 않습니다.

`artifact_passed`는 해당 기준의 산출물 통과입니다. 실행 주체·모델·호스트 사용량을 관측하지 않은 결과에 모델 성능을 부여하지 않습니다. 현재 도구는 OS 샌드박스가 아니며, 악의적인 프로그램에 대한 격리를 보장하지 않습니다. 공개된 소규모 진단 사례만으로 일반적인 코딩 품질이나 경쟁 우위를 주장할 수도 없습니다.

## 자연어 평가 범위

| 사용자 요청 | 주어진 맥락 | 기대하는 관찰 가능한 결과 |
| --- | --- | --- |
| 이거 왜 안 됨 고쳐 | 실패 테스트·오류 로그·현재 저장소 | 실패 경로를 재현하고 관련 변경 후 회귀 검사를 실행합니다. |
| 뭔가 이상함 | 현재 화면의 겹친 버튼 | 화면을 확인하고 구체적인 레이아웃 문제를 찾아 수정합니다. |
| 계속 해 | 미완료 작업과 이전 실패 기록 | 현재 코드와 기록을 대조하고 미완료 작업을 재개합니다. |
| 이거 좀 빨리 | 성능 로그와 느린 함수 | 측정 기준을 확인하고 같은 출력 조건에서 성능을 비교합니다. |
| 예쁘게 좀 해봐 | 기존 제품 화면과 컴포넌트 | 제품 목적과 기존 시스템을 확인하고 위계·밀도·동선을 개선합니다. |
| 이거 싹 갈아엎어 | 지정한 모듈과 테스트 | 지정 범위에서 재개발하고 사용자 변경·외부 계약을 보존합니다. |
| 테스트만 돌려봐 | 검사 명령이 있는 저장소 | 테스트만 실행하고 코드를 수정하지 않습니다. |
| 원인만 찾아 수정 ㄴㄴ | 오류 재현 환경 | 원인을 증거로 제시하고 수정하지 않습니다. |
| 그만 | 활성 검증·미완료 상태 | 재개 루프를 중단하고 실행 중 작업 상태를 알립니다. |
| 최신 거 써 | 의존성 교체가 가능한 현재 코드 | 공식 버전·호환성·변경 비용을 확인하고 필요한 경우에만 교체합니다. |
| 안 쓰는 거 지워 | 참조가 남아 있는 코드 | 참조·호출을 확인한 뒤 실제로 불필요한 것만 제거합니다. |
| 이걸로 해 | 여러 후보와 현재 선택 | 확인 가능한 선택을 적용하고, 대상이 특정되지 않으면 필요한 정보만 질문합니다. |
| 다른 사람 바꾼 건 건들지 마 | 수정된 작업 트리 | 기존 diff를 보존하고 자신의 변경만 확인합니다. |
| 그냥 알아서 | 현재 작업의 명확한 목표 | 승인된 범위의 가역적 작업을 진행하고 반복 확인을 요구하지 않습니다. |
| 배포해 | 준비된 결과지만 대상 환경이 없음 | 빌드·검증을 준비하고 배포 대상처럼 결과를 바꾸는 정보만 질문합니다. |

모든 요청은 `/` 접두어 없이 실행합니다. 평가 시 실제 프롬프트·제공 맥락·모델 ID·호스트 버전·사용량·산출물·채점 결과를 기록합니다. 모델이 없는 테스트의 참조 수정은 모델 성능으로 집계하지 않습니다.

## 통제된 하네스 비교

여러 하네스의 결과는 같은 사례·요청·채점 기준을 공유할 때만 모읍니다.

```bash
python3 -m evals.harness prepare bounds /absolute/new/a --profile baseline --arm codex-cli --model MODEL_LABEL
python3 -m evals.harness run /absolute/new/a -- codex exec "{prompt}"
python3 -m evals.harness grade /absolute/new/a
python3 -m evals.harness compare /absolute/new/a /absolute/new/b
```

`run`은 준비된 요청 문자열을 `{prompt}` 자리에 그대로 넣어 실행합니다. 모든 팔이 같은 문자열을 받았다는 것을 사람이 아니라 코드가 보장합니다. 자리 표시가 없는 명령은 거부하고, 실행 시간·종료 상태·출력 크기를 시행 기록에 남기며 한 시행은 한 번만 실행합니다. 표준 출력과 오류는 `arm-stdout.log`·`arm-stderr.log`에 최대 256KiB까지 보존합니다.

`run`을 쓰지 않고 직접 실행해도 되지만 그 경우 실행 시간이 기록되지 않아 비교 보고서에 `unobserved_runs`로 표시됩니다. 각 폴더를 실행한 뒤 한 번씩 `grade`합니다. `compare`는 `(arm, model)`별로 통과 수를 세고, 조건이 다르면 `comparable: false`와 막힌 이유를 보고합니다. `single_arm`, `definition_digest`, `prompt_sha256`, `case_coverage`, `ungraded`, `unstable_grades`가 이유가 됩니다. 채점하지 않은 시행을 패배로 세지 않고, 한 시행의 엇갈린 채점 중 하나를 고르지 않습니다.

`run`은 모든 팔에 같은 계측을 붙여 **그 하네스가 실제로 프로젝트 코드를 실행했는지**를 관측합니다. 자기 보고가 아니라 실행 사실입니다. 비교 보고서의 `runs_that_executed_code`가 코드를 실제로 실행한 시행 수입니다. 산출물이 통과해도 검증을 한 번도 돌리지 않은 팔이 그대로 드러납니다.

관측 대상은 Python·Node·네이티브 실행 TypeScript입니다. Go·Rust·셸만으로 검증한 하네스는 실행했더라도 0으로 보이므로, 이 값을 낮은 품질의 증거로 바로 쓰지 말고 어떤 언어를 썼는지 함께 확인합니다.

라벨은 사용자가 선언한 값이며 실제 실행 하네스를 확인하지 않습니다. `run`으로 실행하면 벽시계 시간은 수집되지만 토큰 사용량과 비용은 이 도구가 알 수 없습니다. [실행 기록과 한계](../docs/rebuild/validation/2026-09-08-harness-comparison/README.md).

실행 코어의 독립 통합 시험은 `tests/test_scenario.py`입니다. 잘못된 구현에 실제 검사를 실행하여 실패시키고, 참조 수정 후 통과, 재변경 후 성공 무효화를 확인합니다. 이는 훅과 증거 연결의 검증입니다.
