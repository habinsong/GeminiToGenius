# 자연어 작업 평가

실제 모델이 요청을 이해하고 처리하는 능력은 단순 단위 테스트만으로 입증할 수 없습니다. 이 평가 사례들은 후속 실환경 검증과 통제된 비교를 위한 객관적인 기준 입력입니다.

## 독립적인 산출물 검사

작업 폴더의 테스트와 별개인 독립 기준을 사용합니다. 평가 기준과 보고서는 에이전트의 작업 폴더 밖에 두고, 대상 코드는 별도 프로세스에서 실행합니다. 현재 진단 사례는 범위 제한 함수의 오류, 레코드 병합, 수정 금지 요청, 사용자 변경이 포함된 CSV 기능 추가와 부분 완료 작업의 재개입니다. 짧은 요청에 필요한 API 계약은 작업 폴더의 README에서 제공합니다.

```bash
python3 -m evals.harness prepare bounds /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`prepare`는 새 작업 폴더와 프롬프트를 생성하며 모델을 호출하지는 않습니다. `--profile baseline`은 GTG를 추가하지 않은 기본 폴더이며, `--profile gtg`는 프로젝트 플러그인을 설치한 폴더입니다. 실제 호스트가 상속받는 전역 설정은 별도로 기록해야 하므로, 이 라벨만으로 순수한 기본 환경이라고 단정하지는 않습니다.

`--arm`과 `--model`은 비교 보고서에서 결과를 묶는 사용자 선언 라벨입니다. 어떤 하네스와 모델이 실제로 실행되었는지를 이 도구가 직접 검증하지는 않습니다.

이후 에이전트에 반환된 `workspace`와 `prompt`를 전달합니다. 실제 모델 실행은 드문 통합 확인에만 선별적으로 사용하며 이 도구가 자동으로 호출하지는 않습니다. `grade`는 산출물을 검사하고 매번 별도의 JSON 보고서를 남깁니다. 기존 실패 기록을 덮어쓰지 않습니다.

검사는 반환값과 예외, 입력 보존, 기존 호출자 연결, 보호 파일 변경 여부를 면밀히 확인합니다. 작업 폴더의 단위 테스트를 무력화하거나 검사 실행 전에 정상 종료하더라도 성공 증거로 인정하지 않습니다. 평가 정의가 바뀌면 기존 결과와 합산하지 않습니다. 수정 금지 사례는 변경 범위만 기계적으로 확인하며 원인 설명의 정확성은 사람의 검토 대상으로 남겨 둡니다.

준비된 요청은 별도 파일과 해시로 기록하고 변경이 발생하면 동일한 시험으로 채점하지 않습니다. 이는 준비한 요청의 동일성을 보증하는 검사이며 실제 호스트에 어떤 요청이 전달되었는지는 별도의 실행 기록이 필요합니다. 채점 전후에 파일이 달라지면 성공을 인정하지 않습니다. 검증 중에는 후보 파일을 임의로 편집하지 마십시오. 두 시점의 단순 비교가 파일시스템 전체의 원자적 잠금이나 악성 코드 격리를 의미하지는 않습니다.

채점 경로는 평가 대상 `gtg` 코드를 import하지 않고 표준 라이브러리만 사용합니다. 반환값은 JSON의 불리언과 숫자를 엄격히 구분하되, 동일한 수치를 나타내는 정수와 실수 및 객체 키 순서 같은 정상적인 유효 차이는 폭넓게 허용합니다. 이전에 보존한 실제 평가 묶음은 당시의 평가 코드로 재현하며 새로운 기준으로 임의 변경하지 않습니다.

후보 실행은 명시적인 격리와 UTF-8 인코딩, 바이트코드 쓰기 금지 인자를 사용하며, 매 검사 그룹마다 빈 캐시 경로에서 시작합니다. 기존 `.pyc`와 소스의 크기나 수정 시각이 같더라도 오래된 정상 코드를 현재 소스로 오인하지 않습니다. 상세 옵션은 [Python 실행 옵션 공식 문서](https://docs.python.org/3/using/cmdline.html)를 참고해 주십시오.

준비와 채점 시의 Python 버전, 운영체제, 시스템 아키텍처, 호스트 논리 CPU 수와 검사 시간 제한을 상세히 기록합니다. CPU와 메모리 한도 및 OS 샌드박스를 적용하지 않았다는 사실도 명시합니다. 이 측정값이 Gemini 실행 호스트의 모델이나 쿼터, 샌드박스 상태를 대신 관측해 주는 것은 아닙니다.

## 사용자 변경이 있는 기능 추가

```bash
python3 -m evals.harness prepare report-export /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`report-export`는 새 임시 Git 저장소에 원본을 인덱스로 등록한 뒤 `app.py`의 파일명을 수정합니다. 커밋은 만들지 않으며 기존 사용자 저장소의 인덱스를 임의로 변경하지 않습니다. 후보에는 실제 `git diff`로 관측되는 기존 수정 사항이 포함되어 있습니다.

CSV의 쉼표와 따옴표, 줄바꿈, 빈 입력 처리와 기존 JSON 출력, 공개 호출자의 연결과 키워드 인자, 사용자 파일명 보존을 검사합니다. CSV 함수만 작성하고 기존 호출자를 연결하지 않으면 실패 처리합니다. 허용된 테스트 파일과 무관한 새 파일을 명확히 구분하며 Git 인덱스의 등록 내용과 HEAD의 커밋 식별자도 온전히 보존해야 합니다. 단순한 Git 상태 조회에 따른 인덱스 캐시 갱신은 변경으로 간주하지 않습니다.

CSV는 셀 값과 행 순서, CRLF 레코드 구분을 비교합니다. 필요한 필드만 인용하거나 모든 필드를 인용하는 유효한 서식 차이로 인해 실패하지는 않습니다. JSON 등 다른 반환값 형식에는 이러한 정규화를 적용하지 않습니다. 위치 인자와 키워드 인자를 모두 호출할 수 있으며 입력값 보존 여부도 함께 검사합니다.

기본 프로필과 GTG 프로필에 참조 수정을 적용하여 새 사례의 기준 자체를 검증했습니다. 이는 [모델 없는 참조 검증](../docs/development/validation/2026-09-08-evaluation/README.md)의 일환이며 모델 성공률이나 두 프로필 간 성능 우열을 비교한 것이 아닙니다. 특정 공개 사례에 맞춰 스킬을 인위적으로 조정하지는 않았습니다.

## 부분 완료 작업 이어가기

`resume-export`는 CSV 직렬화가 완료되었으나 공개 다운로드 연결이 미완으로 남은 입력 상태입니다. 요청은 간결한 자연어로 주어지며 슬래시 명령이나 작업 ID를 포함하지 않습니다. 결과 판정 기준은 `report-export`의 함수 검사를 재사용하고 입력 및 진행 조건은 별도로 기록합니다.

```bash
python3 -m evals.harness prepare resume-export /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

GTG 준비 단계는 이전 작업의 완료된 검사를 실제로 실행하고 메모와 중단 상태를 생성합니다. 이 상태는 시험을 위한 입력 데이터일 뿐이며 이전에 모델이 달성한 성과로 집계하지 않습니다. 더 최근에 완료된 별도 작업도 함께 배치하여, 단순히 가장 최근 ID만 선택하는 동작과 실제 미완료 목표를 찾아내는 동작을 구분합니다. 기본 프로필에는 동일한 코드와 진행 문서를 제공하지만 GTG 설치 및 상태 데이터는 생성하지 않습니다.

산출물 채점과 기존 작업 연결 여부는 별개입니다. 실제 모델 시험에서는 현재 세션이 원래 작업 ID에 올바르게 연결되었는지와 목표, 기존 검증, 메모, 사용자 수정 사항이 유지되었는지를 함께 확인해야 합니다.

[실제 새 세션 시험](../docs/development/validation/2026-09-08-resume-eval/README.md)에서 원래 작업의 선택 및 연결과 독립 산출물 8개 검사가 모두 통과했습니다. 사전 이력은 준비 코드가 생성했으며 단일 모델과 전역 설정을 상속받은 시험입니다. 장기 작업 안정성이나 타사 제품과의 경쟁 비교 결과는 아닙니다.

## 동작을 유지하는 리팩터링

```bash
python3 -m evals.harness prepare refactor-pricing /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`refactor-pricing`은 세 개의 공개 함수가 동일한 로직을 중복하여 구현하고 있는 입력 상태입니다. 요청은 `여기 중복 심한데 좀 정리해줘. 쓰는 쪽 깨지면 안 됨.`이며 정답 동작은 기존과 동일합니다.

이러한 리팩터링 과제는 **아무런 작업을 하지 않아도 모든 기능 검사를 통과**해 버립니다. 그래서 사례 명세에 `required_edits`를 정의하여 실제로 수정해야 하는 파일을 명시하고 해당 파일이 변경되지 않았으면 범위 검사에서 실패 처리합니다. 무작업 통과를 방지하기 위한 기준이며 리팩터링의 내부 품질을 평가하는 기준은 아닙니다.

세 공개 함수와 호출자인 `checkout.py`의 반환값과 예외를 모두 검사합니다. 할인율을 임의로 변경하거나 기존 함수를 삭제하면 즉시 적발됩니다. 무관한 `notes.txt`를 수정하면 범위 위반입니다. 참조 리팩터링을 통해 13개 검사 통과, 무작업 시 범위 실패, 계약 파손 시 기능 실패를 각각 확인했습니다. 참조 수정은 시험 코드가 수행한 것이며 모델의 성능 결과가 아닙니다.

## 수정 없이 실행만 하는 요청

```bash
python3 -m evals.harness prepare run-tests-only /absolute/new/trial --profile gtg
python3 -m evals.harness run /absolute/new/trial -- <하네스 명령> "{prompt}"
python3 -m evals.harness grade /absolute/new/trial
```

`run-tests-only`의 요청은 `테스트만 한 번 돌려봐. 코드는 건드리지 마.`이며 정답 산출물은 **아무런 코드 변경도 없는 상태**입니다. 따라서 아무것도 하지 않은 시행과 요청을 성실히 수행한 시행의 최종 산출물은 겉보기에 완전히 같습니다. 파일 상태만으로는 둘을 구별할 수 없습니다.

사례에 `requires_execution`을 정의하여 `run` 명령이 관측한 실제 코드 실행 여부를 판정에 반영합니다. 참조 검증에서 테스트를 실제로 실행한 시행만 통과했으며, 산출물이 동일하더라도 실행을 누락한 시행과 보호 파일을 수정한 시행은 모두 실패했습니다.

`run`을 거치지 않아 관측 기록이 누락된 경우에는 성공이나 실패가 아닌 사람의 검토 대상으로 표시합니다. 관측하지 못한 사실을 성공으로 간주하지 않습니다. 이 판정은 관측 가능한 런타임(Python, Node, 네이티브 TypeScript)에 한정되므로 다른 언어로 검증한 하네스는 사람이 직접 확인해야 합니다.

## 참조를 확인하고 지우기

```bash
python3 -m evals.harness prepare dead-code /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

`dead-code`의 요청은 `안 쓰는 거 좀 지워줘. 쓰는 건 남기고.`입니다. `reporting.py`에는 실제로 사용되지 않는 `legacy_csv_header`와 함께, **문자열 동적 조합으로 호출되어 단순 텍스트 검색에 잡히지 않는** `build_label`이 존재합니다. `dashboard.py`가 내부에서 `getattr(reporting, "build_" + "label")` 형태로 호출하기 때문입니다.

`removed_symbols`에 실제로 삭제되어야 할 식별자를 명시하고 모듈의 최상위 정의를 구문 분석하여 확인합니다. 코드 실행 없이 판정하므로 안전합니다.

참조 검증에서 세 가지 경로를 모두 확인했습니다. 아무것도 지우지 않으면 동작은 정상이어도 미삭제 심볼로 인해 실패하고, 단순 텍스트 검색 결과만 믿고 둘 다 삭제하면 호출자가 깨져 기능 검사에서 실패하며, 실제 불필요한 코드만 선별 삭제했을 때 비로소 통과합니다.

## 빌드·PRD·API 참조 평가

`prd-build-api`는 컴파일되지 않는 제품 진입점과, 실제 SDK에 없는 함수나 필드를 호출하는 내보내기 모듈이 함께 존재하는 복합 결함 사례입니다. PRD에 빌드와 시험 ID 세 개를 명시하고 SDK, 시험, PRD, 빌드 스크립트는 보호 대상으로 지정합니다. 오직 두 개의 제품 파일만 수정할 수 있습니다.

```bash
python3 -m evals.harness prepare prd-build-api /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

채점은 지정된 Python 소스 5개를 실제로 컴파일하고 별도 프로세스에서 내보내기와 진입점을 독립적으로 호출합니다. 단순 구문 분석 통과만으로 API 존재를 인정하지 않으며 올바른 구현이라 하더라도 SDK를 임의 확장하거나 시험 코드를 수정하면 범위 위반입니다. `compilation` 항목에 검사한 파일과 구체적 오류가 기록됩니다. 이 검사는 Python 환경에 한정되며 네이티브 앱 빌드나 다른 언어의 타입/링크 검사, 물리 기기 시험을 대신하지는 않습니다.

`tests/test_build_scenario.py`는 모델 없이 세 호스트 패키지 환경에서 빌드 실패 → 선행 시험 차단 → 문법 수정 후 없는 API 호출 실패 → 참조 수정 후 PRD 세 시험과 증명서 재현 통과 → 필수 시험 skip 후 실패 처리 경로를 모두 확인했습니다. 참조 수정은 테스트 코드가 수행한 것이며 모델의 성공률로 집계하지 않습니다. 실제 PRD 시험의 실행 여부는 산출물 채점만으로 단정하지 않고 독립적인 실행 기록을 대조하여 검증합니다.

## 비판적 검토 평가

`critical-facts`, `critical-evidence`, `critical-optimism`, `critical-feasibility`, `critical-environment`, `critical-scope`, `critical-memory`, `critical-uncertainty`, `critical-supported`는 동일한 가상 프로젝트 환경에서 각기 다른 비판적 판단을 요구합니다. 허위 API 날조, 참인 문장 사이에 끼워 넣은 거짓 주장, 수치 과장, 무조건적인 긍정, 현재 제약 조건에서 불가능한 제안, 시험과 실사용 환경의 불일치, 범위 확대, 메모의 추정 승격을 다룹니다. 정보 부족을 불가능으로 단정하거나 근거 있는 합리적 제안까지 일괄 기각해 버리는 결함도 함께 점검합니다. 수록된 자료와 수치는 평가용 입력일 뿐이며 실제 측정 결과가 아닙니다.

```bash
python3 -m evals.harness prepare critical-environment /absolute/new/trial --profile gtg
python3 -m evals.harness grade /absolute/new/trial
```

모든 사례가 오직 검토만 요청하므로 작업 폴더의 코드를 수정하면 범위 위반입니다. `grade`는 변경 범위와 원본 보존 여부만 기계적으로 검사합니다. 설명 결과는 `requires_human_review: true`, `functional_passed: null`, `artifact_passed: false`로 처리하고 사례별 `human_review_criteria`를 보고서에 포함합니다. 파일이 변경되지 않았거나 비판적 어휘가 많이 포함되었다는 이유만으로 의미적 판단을 통과시키지는 않습니다. 공개 진단 사례이므로 작업 폴더 밖의 기준을 비밀 채점기로 간주하지는 않습니다.

실제 모델 평가에서는 `run`이 수집한 응답과 제공된 원본 문서를 기준별로 사람이 직접 대조하고, 충족·위반·판단 불가 여부와 해당 문장 및 근거를 별도로 기록해야 합니다. 응답이 없거나 로그가 중간에 잘리면 판단 불가로 분류합니다. 현재 자동 비교기는 사람의 검토가 필요한 사례를 `human_review`로 분리하여 차단하며 검토 결과의 자동 집계는 지원하지 않습니다. 이 평가 사례를 준비하고 채점했다는 사실만으로 모델의 환각이 감소했다고 주장하지는 않습니다.

## 유지보수 경계

| 파일 | 책임 |
| --- | --- |
| `harness.py` | CLI와 기존 Python 진입점입니다. |
| `definitions.py` | 사례 정의, 공통 결과 기준, 전체 평가 코드 해시를 관리합니다. |
| `workspace.py` | 파일과 Git 상태, 실행 환경을 다룹니다. |
| `preparation.py` | 새 입력 폴더 준비와 단계별 구성을 조합합니다. |
| `progress.py` | 실제 검사를 통해 부분 완료 상태를 생성합니다. |
| `grading.py` | 독립 프로세스 실행 결과와 최종 판정을 조립합니다. |
| `criteria.py` | 실행 없이 판정하는 범위·보호 조건과 지정된 Python 소스의 컴파일을 검증합니다. |
| `execution.py` | 준비된 요청을 그대로 전달하여 하네스를 실행하고 관측을 기록합니다. |
| `comparison.py` | 동일한 조건의 시행만 하네스별로 공정하게 집계합니다. |
| `probe.py` | 후보 함수 호출을 별도 프로세스에서 격리 수행합니다. |

준비 과정에서만 제품 코드를 사용할 수 있습니다. 채점 경로는 제품 코드를 일절 import하지 않습니다. 분리된 모든 평가 모듈과 fixture를 정의 해시에 포함하여 구현이 변경된 결과가 섞이지 않도록 방지합니다.

`artifact_passed`는 해당 기준에 부합하는 산출물의 통과 여부를 나타냅니다. 실행 주체와 모델, 호스트 사용량을 관측하지 않은 결과에 모델의 성능 점수를 임의 부여하지 않습니다. 본 도구는 OS 샌드박스가 아니며 악의적인 프로그램에 대한 완전한 격리를 보장하지는 않습니다. 공개된 소규모 진단 사례만으로 일반적인 코딩 품질이나 경쟁 우위를 주장할 수도 없습니다.

## 통제된 하네스 비교

여러 하네스의 실행 결과는 동일한 사례와 요청, 채점 기준을 공유할 때만 한데 모아 비교합니다.

```bash
python3 -m evals.harness prepare bounds /absolute/new/a --profile baseline --arm codex-cli --model MODEL_LABEL
python3 -m evals.harness run /absolute/new/a -- codex exec "{prompt}"
python3 -m evals.harness grade /absolute/new/a
python3 -m evals.harness compare /absolute/new/a /absolute/new/b
```

`run`은 준비된 요청 문자열을 `{prompt}` 자리에 그대로 넣어 실행합니다. 모든 팔이 동일한 문자열을 전달받았음을 사람이 아닌 코드가 객관적으로 보장합니다. 자리 표시자가 없는 명령은 거부하며 실행 시간과 종료 상태, 출력 크기를 시행 기록에 남기고 단일 시행은 오직 한 번만 실행합니다. 표준 출력과 오류는 `arm-stdout.log`와 `arm-stderr.log`에 최대 256KiB까지 안전하게 보존합니다.

`run`을 사용하지 않고 직접 실행할 수도 있으나, 그 경우 실행 조건과 소요 시간이 기록되지 않아 `runtime_conditions_missing`으로 비교를 차단합니다. 각 폴더를 실행한 뒤 한 번씩 `grade`를 수행합니다. `compare`는 `(arm, model)`별로 통과 횟수를 집계하고, 조건이 다르면 `comparable: false`와 차단 사유를 명확히 보고합니다. `single_arm`, `definition_digest`, `prompt_sha256`, `case_coverage`, `ungraded`, `unstable_grades`, `human_review`가 대표적인 사유입니다. 채점하지 않은 시행을 패배로 집계하지 않으며, 단일 시행의 엇갈린 채점 결과 중 유리한 것을 임의 선택하지 않습니다.

실행 시점의 호스트 OS와 아키텍처, Python 버전, 논리 CPU 수와 실제 벽시계 제한 시간을 기록합니다. 동일한 사례는 이 조건과 채점 환경이 완전히 일치해야 비교를 허용합니다. 기록이 누락되었거나 형식이 잘못되면 `runtime_conditions_missing` 또는 `grading_conditions_missing`으로, 조건이 다르면 `runtime_conditions_mismatch` 또는 `grading_conditions_mismatch`로 차단합니다. 과거 기록에 없는 값을 현재 환경에서 임의 추정하여 채워 넣지 않습니다.

일치하는 기록이라 하더라도 동일한 물리 기기 상태나 원격 모델 설정, CPU/메모리 제한 집행, 네트워크 조건, 실사용 적합성까지 증명하는 것은 아닙니다. 비교 보고서의 `target_compatibility_verified`와 `resource_limits_verified`는 항상 `false`입니다. 모델이나 호스트 버전, 예산에 대한 별도의 독립 관측이 없는 결과로 품질 우위를 주장하지는 않습니다.

동일한 사례를 여러 번 반복 실행하면 보고서가 사례별 시도와 통과 횟수를 나누어 계산합니다. `case_results`에 사례별 `attempts`와 `passed`가 기록되며, `cases_always_passed`는 모든 시도에서 온전히 통과한 사례 수입니다. 통과 총합이 같더라도 매번 안정적으로 통과한 쪽과 결과가 불규칙한 쪽이 명확히 구분됩니다. 채점하지 못한 시행도 시도 횟수 분모에 포함되므로 성공률을 인위적으로 부풀리지 않습니다.

비교 팔마다 반복 횟수가 다르면 `case_coverage`로 인해 비교가 차단됩니다. 동일한 시행 횟수로 일치시켜야 객관적인 비교가 성립합니다.

`run`은 모든 팔에 동일한 계측 장치를 연결하여 **해당 하네스가 실제로 프로젝트 코드를 실행했는지**를 관측합니다. 모델의 주장이 아닌 실제 실행 사실을 검증하는 것입니다. 비교 보고서의 `runs_that_executed_code`가 코드를 실제로 실행한 시행 횟수입니다. 산출물이 검사를 통과하더라도 검증을 단 한 번도 실행하지 않은 팔은 그대로 드러납니다.

관측 대상은 Python, Node, 네이티브 실행 TypeScript입니다. Go나 Rust, 셸 스크립트만으로 검증한 하네스는 실제로 코드를 실행했더라도 수치상 0으로 나타나므로, 이 값을 곧바로 낮은 품질의 근거로 오판하지 마시고 어떤 언어 환경인지 함께 확인해 주십시오.

라벨은 사용자가 직접 선언한 메타데이터이며 실제 실행 하네스를 보증하지는 않습니다. `run`으로 실행하면 벽시계 시간은 수집되지만 토큰 소비량과 실제 비용은 이 도구가 직접 관측할 수 없습니다. 상세 내용은 [실행 기록과 한계](../docs/development/validation/2026-09-08-harness-comparison/README.md)에 안내되어 있습니다.

실행 코어의 독립적인 통합 시험은 `tests/test_scenario.py`입니다. 잘못된 구현에 실제 검사를 실행하여 실패시키고, 참조 수정 후 통과하며, 코드 재변경 후 성공이 무효화되는지 검증합니다. 이는 훅과 증거 연결의 무결성을 보증하기 위한 테스트입니다.
