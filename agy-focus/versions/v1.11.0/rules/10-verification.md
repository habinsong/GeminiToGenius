# 10 검증

- 변경 작업은 상태 확인 → 한 가지 변경 → 가장 작은 직접 검증 순서로 진행합니다.
- 시작할 때 내부적으로 `목표·범위·완료 조건`을 고정하고, 종료 전 세 항목을 실제 증거와 대조합니다.
- 테스트·빌드·실행·UI 확인을 하지 않았다면 통과했다고 말하지 않습니다.
- 실패하면 같은 명령을 맹목적으로 반복하지 말고 원인 가설 하나를 세워 재검증합니다.
- 검증 결과가 없는 추정과 완료 판정을 섞지 않습니다.
- 내부 사고 과정을 장황하게 출력하지 말고 결론·근거·실행한 검증·남은 리스크만 보고합니다.

## UI·웹 결과 품질 게이트

- 헤드라인과 본문을 읽었을 때 실제 기능·대상·다음 행동이 드러나는지 확인합니다. 설명을 길게 늘여 쓰는 AI 특유의 서술형 텍스트, AI Slop·AI SaaS 카피, 모호한 미래 약속은 제거합니다.
- 화면의 시각적 위계가 기능 순서와 맞는지 확인합니다. 동일한 여백·동일한 둥근 모서리·반복 카드만으로 화면을 채우거나 기계적으로 정렬하지 않습니다.
- 배경·버튼의 다채로운 또는 보라색→파란색 그라데이션, 요술봉 같은 추상 아이콘, 작위적인 3D 이미지가 장식으로 들어갔는지 확인하고 근거가 없으면 제거합니다.
- Hover·전환·마이크로 인터랙션과 시각 효과마다 사용자 목표·상태 변화·피드백이라는 목적이 있는지 확인합니다. 목적이 없으면 넣지 않습니다.
- 폰트·카피·이미지가 제품 맥락과 실제 대상을 식별하게 하는지 확인합니다. `Inter` 기본값과 추상적 카피·이미지 사용을 결과물의 품질 기준으로 통과시키지 않습니다.
