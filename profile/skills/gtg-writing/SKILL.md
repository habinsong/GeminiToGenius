# 사람이 읽는 글

좋은 글은 독자가 다음에 무엇을 하면 되는지 빨리 알게 해 주는 글이고, 그러려면 꾸밈말을 보태기보다 확인한 사실을 순서대로 이어 쓰는 편이 낫습니다.

## 쓰는 순서

1. 독자와 목적을 한 줄로 정합니다. 누가 읽고 읽은 뒤 무엇을 하거나 알게 되어야 하는지 정해 두면, 넣을 내용과 뺄 내용이 저절로 갈립니다.
2. 쓸 사실은 근거에서 가져옵니다. 숫자·이름·버전·결과는 확인한 파일과 실행 결과, 원문에서만 가져오고 근거가 없으면 쓰지 않거나 미확인으로 둡니다. 윤문할 때도 원문에 없던 사실이나 교훈을 보태지 않습니다.
3. 말하듯 초안을 씁니다. 이어지는 생각은 연결어미(`~하고`, `~해서`, `~인데`, `~지만`)로 한 문장에 묶어 두고, 짧은 문장은 강조하거나 방향을 바꿀 때만 씁니다. 주어는 실제로 움직이는 사람·팀·코드입니다.
4. 걷어냅니다. 상투구, 의의 부풀리기, 결론 신호어, 습관적인 세 개 나열, 굵은 글씨 남발, 독자가 묻지 않은 기술 설명을 지우되 지운 자리에 다른 상투구를 넣지는 않습니다.
5. 아래 `prose` 검사를 돌립니다.
6. 소리 내어 읽듯 다시 읽습니다. 숨이 막히게 긴 문장은 나누고 뚝뚝 끊기는 문장은 이으면, 문장 사이에 자연스러운 호흡이 생깁니다.

## 과서술과 이상한 기술 서술

독자가 묻지 않은 내부 구조는 설명하지 않습니다. `SHA-256 해시 매니페스트 기반 무결성 검증 파이프라인`처럼 기술 명사를 겹겹이 붙이는 대신, 그 장치가 독자에게 무엇을 해 주는지를 동사로 씁니다(`설치 파일이 바뀌었으면 설치를 멈춥니다`). 같은 내용을 제목과 첫 문장과 마지막 문장에서 세 번 말하지 않고, 한 문단에는 이야기 하나만 담아 끝에 요약이나 교훈을 덧붙이지 않습니다.

언어별 버릇과 고친 예는 [한국어](references/korean.md)와 [영어](references/english.md)에 있습니다.

## 검사

```bash
python3 "$GTG_RUNNER" prose --workspace /absolute/project/path README.md docs/guide.md
```

결과의 `blocking`이 0이 아니면 종료 코드 1입니다. 차단 항목은 지워도 뜻이 줄지 않는 상투구라 모두 고치고, 검토 항목은 사람도 쓰는 표현이 한 문단에 몰렸거나 문장 리듬이 단조로운 경우라서 문맥에 맞으면 남기되 이유를 짧게 적습니다. 코드 블록과 인라인 코드, URL은 보지 않으니 나쁜 예를 인용할 때는 인라인 코드로 감쌉니다.

이 검사는 표현 목록과 문장 길이만 봅니다. 통과했다고 좋은 글이라는 뜻이 아니고 내용이 맞는지도 확인하지 않으며, 검사를 넘기려고 단어만 비슷한 말로 바꾼 것은 고친 것이 아닙니다. 문장 구조를 바꾸세요. 문서 작업을 작업 계약에 등록할 때는 이 명령을 검사로 넣고 고친 문서를 watch에 둡니다.

## 답변과 보고

채팅 답변과 완료 보고도 같은 기준으로 씁니다. 첫 문장에 결론이나 결과를 쓰고 그 뒤에 근거와 남은 일을 이어 쓰며, `좋은 질문입니다`나 `도움이 되셨으면 좋겠습니다` 같은 인사말은 붙이지 않습니다. 목록은 항목이 정말 나란할 때만 쓰고, 이야기가 이어지는 내용은 문단으로 씁니다.
