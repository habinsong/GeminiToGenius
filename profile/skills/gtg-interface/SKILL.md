# 화면 구현과 검증

현재 화면과 제품의 주요 작업을 먼저 보고, 사용자가 어디서 막히는지 구체적으로 짚습니다. 기존 디자인 시스템과 컴포넌트가 있으면 그것을 따르고 색·페이지 수·카드·모션을 미리 정해 둔 틀에 끼워 맞추지 않는데, 화면 구조는 그런 틀이 아니라 정보의 우선순위와 사용자 동선에서 나오기 때문입니다.

필요한 경로와 로딩·빈 상태·오류·선택·복구 동작을 계획합니다. 복잡한 UI라면 계획과 확인할 상태를 로컬 문서로 남기지만, 작은 수정마다 긴 계획서를 쓰지는 않습니다.

실제로 동작하는 인터랙션을 만듭니다. 가짜 지표, 눌러도 아무 일이 없는 버튼, 제품과 상관없는 장식은 넣지 않습니다. 화면 문구는 `gtg-writing`의 기준대로, 사용자가 지금 상황과 다음 행동을 바로 알 수 있게 짧고 구체적으로 씁니다. `혁신적인`, `강력한`, `원활한` 같은 홍보 문구 대신 그 버튼이 하는 일을 씁니다.

지원되는 브라우저나 앱 도구로 실제 화면과 동선을 확인합니다. 작업 범위에 맞춰 좁은 화면과 넓은 화면의 넘침, 키보드 이동과 포커스, 읽기 순서, 직접 URL 접근과 뒤로 가기, 움직임 줄이기 설정을 점검합니다. 스크린샷을 만든 것과 사람이 읽을 만한 화면인지 확인한 것은 다른 일입니다.

DOM의 단어나 계획서 분량, 페이지 수로 화면 품질을 판정하지 않습니다. 시험과 실제 시각 관찰을 연결하고, 도구가 없어 확인하지 못한 항목은 미검증으로 남깁니다.

화면이 만들어졌다는 이유만으로 좋은 결과라고 보지 않습니다. 목 데이터, 자동화 전용 설정, 다른 브라우저나 에뮬레이터에서의 결과를 실제 사용자 환경의 성공으로 넓히지 않습니다. 핵심 호환성이나 실사용 조건이 불확실하면 [적대적 검토](../gtg-build/references/critical-review.md)를 적용합니다.
