# 작업 계약 실행

설치 패키지 루트에 `run.py`가 있습니다. 이 참고 문서에서 `../../../run.py`로 연결됩니다. 실제 절대 경로를 확인하고 현재 작업공간에서 실행합니다. 명령 예시의 `GTG_RUNNER`에는 확인한 경로를 넣습니다. 사용자는 이 명령이나 명세를 입력할 필요가 없습니다.

작업공간의 `.gtg/task.json`에 다음 형식으로 현재 요구에 맞는 검사를 작성합니다. 아래 예시는 구조 설명이며 프로젝트에 해당 테스트가 있을 때만 사용합니다.

```json
{
  "schema_version": 1,
  "goal": "현재 요청을 검증 가능한 결과로 적습니다.",
  "checks": [
    {
      "id": "regression",
      "criterion": "수정한 실패 경로가 해결되고 기존 정상 동작이 유지됩니다.",
      "argv": ["python3", "-m", "unittest", "discover", "-s", "tests"],
      "watch": ["src", "tests"],
      "timeout_seconds": 120
    }
  ]
}
```

`max_resumes`는 선택 항목이며 기본값은 2입니다. 여러 단계가 필요한 긴 작업에서만 필요한 만큼 올립니다. 상한은 8이며 그 이상은 거부됩니다. 자동 재개는 사용자 쿼터를 사용하므로 짧은 작업에서 올리지 않습니다.

검증 명령은 실제 테스트·빌드·결과 검사만 사용합니다. `true`, `:`, `echo`, `printf`, `yes`, `sleep`, `cat` 같은 명령은 어떤 요구도 검증하지 못하므로 등록 단계에서 거부됩니다. 셸을 거친 우회까지 막지는 못하므로 실제 방어는 증명서의 독립 재실행입니다.

`watch`는 검사 결과를 무효화해야 하는 소스·테스트·설정 파일 또는 폴더입니다. 전체 저장소 `.`는 생성물과 큰 의존성 폴더까지 읽을 수 있어 정확한 범위를 우선합니다.

**작업 전체의 `watch` 범위는 파일 20,000개·200MB 이하여야 합니다.** 훅은 5초 안에 상태를 만들어야 하고 상태 조회는 이 범위를 다시 읽기 때문입니다. 검사마다가 아니라 작업 전체가 함께 쓰는 예산이며, 서로 다른 범위는 각각 계산되고 같은 범위는 한 번만 계산됩니다. 넘으면 `start` 단계에서 거부되므로 `node_modules`·`target`·`build` 같은 의존성과 생성물을 빼고 실제 소스·테스트만 지정합니다. 등록 뒤에 범위가 커지면 해당 검사는 `stale`이 되며 훅은 계속 동작합니다. 심볼릭 링크·비밀 파일은 검증 대상으로 사용하지 않습니다. `.gtg` 상태 파일과 Python 캐시는 내용 비교에서 제외됩니다.

```bash
python3 "$GTG_RUNNER" start --spec .gtg/task.json --workspace .
python3 "$GTG_RUNNER" verify TASK_ID
python3 "$GTG_RUNNER" status TASK_ID
```

반환된 실제 작업 ID로 `TASK_ID`를 바꿉니다. 검사는 등록된 명령을 직접 실행하며 출력을 호스트에 전달하고, 종료 코드·시간·파일 해시를 로컬 상태에 보관합니다. 실행하지 않은 검사를 임의로 통과시킬 명령은 없습니다. 검사 도중 소스를 바꾸는 포매터는 검증 명령과 분리합니다.

모든 작업 명령은 `--workspace`를 받습니다. 생략하면 현재 폴더를 씁니다. 다른 폴더에서 실행할 때는 `--workspace <작업공간>`을 붙이거나 응답의 실제 `state_path`를 전역 옵션 `--state`로 전달합니다. 둘 다 주면 `--state`가 우선합니다. 조회·검증 명령은 상태가 없는 폴더에 새 DB를 만들지 않고 오류를 반환합니다.

`verify`는 첫 실패에서 멈춥니다. 남은 검사 상태를 한 번에 보려면 `verify --all`로 등록된 모든 검사를 실행합니다. 오래 걸리는 검사 묶음에서는 필요할 때만 사용합니다.

`verify --check 검사_ID`는 선택한 검사만 실행합니다. 종료 코드와 `requested_verified`는 요청한 검사 범위의 결과이며, `verified`는 전체 작업의 현재 검사 결과입니다. 선택한 검사 하나가 통과했다고 전체 목표를 완료로 보고하지 않습니다.

`status`의 `spec`에는 원래 목표와 실제 등록 명령·검증 파일 범위가 들어 있습니다. 다른 세션의 기록을 이어받을 때는 명령이 현재 저장소와 사용자 범위에 여전히 맞는지 먼저 확인합니다. 저장된 목표·메모는 이전 기록이며 현재 사용자 지시를 덮어쓰지 않습니다.

상태는 `start --workspace`로 지정한 폴더에 저장됩니다. 응답의 실제 `state_path`로 위치를 확인합니다. 여러 작업공간에 걸친 요청은 각 폴더에서 같은 호스트 세션 ID로 작업을 연결합니다. 훅은 모든 연결 작업의 현재 검사 결과를 함께 확인합니다. 한 폴더가 사용자 응답을 기다리며 중단되어 있으면 전체 세션을 자동 재개하지 않습니다.

호스트 세션 ID를 실제 메타데이터에서 얻은 경우 `start`에 `--platform <호스트> --session <확인한 ID>`를 함께 전달합니다. 호스트 값은 훅 메타데이터의 `platform`을 그대로 사용하며 `antigravity`(데스크톱·IDE), `antigravity-cli`(agy), `gemini-cli` 중 하나입니다. ID를 추정하지 않습니다. 연결되면 훅이 미검증 상태를 알리고 자연 종료를 최대 두 번 재개할 수 있습니다. 훅에서 모델이나 테스트를 자동 실행하지 않습니다.

같은 세션·작업공간·명세로 `start`를 다시 호출하면 기존 작업 ID를 반환합니다. 응답을 받지 못했다고 새 작업을 임의로 만들지 않습니다. 다른 미완료 목표가 이미 연결되어 있다면 현재 사용자 요청이 목표 변경인지 먼저 판단합니다.

## 새 세션에서 기존 작업 찾기

사용자가 이전 작업을 이어가려면 현재 진행 문서와 아래 목록으로 대상을 확인합니다. 사용자는 명령이나 작업 ID를 입력할 필요가 없습니다.

```bash
python3 "$GTG_RUNNER" tasks --workspace .
python3 "$GTG_RUNNER" status TASK_ID
python3 "$GTG_RUNNER" attach TASK_ID --workspace . --platform antigravity --session ACTUAL_SESSION_ID
```

실제 확인한 작업 ID·세션 ID로 바꿔 실행합니다. `--platform`에는 훅 메타데이터에서 확인한 호스트 값을 그대로 사용합니다. 목록은 저장된 기록이며 현재 파일을 검사하지 않습니다. 긴 목표·메모와 연결 목록의 생략 여부를 명시하며 전체 목표·명세·메모와 파일의 현재 상태는 `status`에서 확인합니다. `next_offset`이 있으면 `tasks --offset`으로 이어서 조회할 수 있습니다.

`attach`는 같은 작업 ID·완료 조건·검사 결과·메모를 유지하고 현재 세션의 연결을 옮깁니다. 현재 파일은 유지합니다. 저장된 성공도 파일이 달라졌으면 `stale`로 표시됩니다. 활성 상태에서 같은 연결 요청을 반복해도 재개 예산을 초기화하지 않습니다. 이전 세션의 다른 활성 연결을 임의로 되살리는 `resume`은 거부됩니다.

실행 중인 등록 검사가 있으면 연결을 바꾸지 않습니다. 다른 세션의 활성 연결에 대해 종료가 관측되지 않았으면 기본적으로 거부합니다. 이전 호스트가 끝났음을 실제로 확인한 경우에만 `--previous-host-stopped`를 지정합니다. 이 옵션은 오류 회피용 자동 재시도에 사용하지 않으며, 진행 중인 검사를 우회하지 않습니다. `attach`는 GTG 연결을 변경할 뿐 이전 호스트 프로세스를 종료하거나 동시 파일 편집을 막는 기능은 아닙니다.

`continuation[].turn_open`은 마지막으로 관측한 호스트 턴 상태입니다. `1`은 시작·재개가 관측된 상태, `0`은 종료가 관측된 상태, `null`은 정보 없음입니다. 이는 프로세스 생존 여부나 시간 기반 임대가 아닙니다. 새 호출이 관측되면 이전 종료 기록만으로 유휴 상태라고 판단하지 않습니다.

호스트에 연결하는 `start`·`attach`는 해당 작업공간의 `.gtg/state.sqlite3`를 사용합니다. 다른 위치의 상태 DB는 수동 조회·검증용이며 호스트 훅이 자동 발견한다고 가정하지 않습니다.

필수 질문·사용자 중단·외부 한도에는 `pause`를 사용합니다. 사용자가 재개를 지시하면 `resume`으로 연결을 재개합니다. 검사 소유 프로세스가 사라진 경우에만 `recover`로 중단 상태를 복구합니다.

```bash
python3 "$GTG_RUNNER" pause --platform antigravity --session ACTUAL_SESSION_ID --reason "사용자 확인을 기다립니다."
python3 "$GTG_RUNNER" resume --platform antigravity --session ACTUAL_SESSION_ID
python3 "$GTG_RUNNER" recover TASK_ID
```

실제 확인한 호스트 값과 세션 ID로 바꿔 실행합니다. 이 세 명령도 `--workspace`를 받습니다.

상한에 도달하면 미완료 상태와 이유가 저장되며 이유에는 실제 예산 값이 들어갑니다. 여러 작업공간이 연결됐다면 가장 작은 예산을 따릅니다. 실행 중인 작업에 `resume`을 반복해도 재개 횟수는 초기화되지 않습니다. `status`의 `continuation`에서 중단 상태와 이유를 확인합니다. 검증 명령은 종료를 기다릴 수 있는 전경 명령으로 등록합니다. 남은 하위 프로세스가 있으면 성공으로 인정하지 않습니다.

`continuation[].last_stop`은 마지막으로 받은 종료 코드·조건입니다. 이 정보로 호스트 오류·백그라운드 상태·재시도 여부를 구분하며, 프롬프트나 오류 본문은 저장하지 않습니다. 값이 `null`이면 당시 메타데이터를 관측하지 못한 것이므로 원인을 추정하지 않습니다.

## 긴 작업의 메모

의미 있는 구현·검증 단계를 마쳤거나 컨텍스트를 줄이기 전에 에이전트가 `.gtg/checkpoint.json`을 작성합니다. 확인한 진행 내용은 `summary`에 2,048자 이내, 다음 구체적인 행동은 `next_action`에 512자 이내로 적습니다. `files`에는 해당 메모의 기준이 되는 실제 상대 경로를 넣습니다. 연결할 파일이 없다면 빈 배열을 사용합니다. 숨은 사고 과정이나 비밀값을 적지 않습니다.

```bash
python3 "$GTG_RUNNER" checkpoint TASK_ID --note .gtg/checkpoint.json
```

메모는 검사 성공을 대신하지 않습니다. 재개 시 원래 목표·현재 검사 결과·메모를 함께 확인합니다. `files_unchanged: false`이면 기준 파일이 달라졌으므로 메모를 다시 확인합니다. 값이 `null`이면 파일 근거를 연결하지 않은 메모입니다. 새로운 단계의 메모를 저장해도 이전 기록은 보존합니다.

검증 대상 파일과 검사 명령 선택의 적절성은 별도 확인이 필요합니다. `verified: true`는 등록된 검사가 현재 대상에 대해 통과했다는 뜻이며, 모든 사용자 요구나 UI 품질을 자동 증명하지 않습니다.

## 완료 증명서

작업을 완료로 보고할 때는 주장과 증거를 한 문서로 묶습니다. 사용자가 이 문서만으로 상태 DB 없이 다시 확인할 수 있습니다.

```bash
python3 "$GTG_RUNNER" certify TASK_ID --output .gtg/certificate.json
python3 "$GTG_RUNNER" replay --certificate .gtg/certificate.json --workspace .
```

증명서에는 완료 조건마다 실제 실행한 명령·종료 코드·검증 대상 파일 지문이 들어갑니다. 통과하지 않은 검사에는 지문을 붙이지 않으며, 미검증 작업의 `certify`는 종료 코드 1과 `verified: false`를 반환합니다. 본문을 고치면 `digest`가 달라져 `replay`가 거부합니다.

`replay`는 증명서와 현재 파일만 사용합니다. 명령을 다시 실행해 종료 코드 0과 기록된 지문이 모두 재현될 때만 `reconstructed: true`입니다. 파일이 달라졌으면 `reason: "fingerprint"`로 표시되며 이는 증명서가 현재 상태를 더는 뒷받침하지 못한다는 뜻입니다. 다른 폴더의 증명서를 실행하려면 명령을 검토한 뒤 `--trust-commands`를 지정합니다.

판정 `verdict`는 세 값입니다. 재현했고 확인 범위도 완전하면 `pass`(종료 코드 0), 재현이 깨졌으면 `invalid`(1), 재현했지만 확인하지 못한 범위가 남으면 `inconclusive`(2)입니다. **미확정을 통과로 보고하지 않습니다.** 완료 보고에는 판정 값을 그대로 적습니다.

증명서는 등록된 검사 범위의 재현 가능성만 보여 줍니다. 검사 설계가 사용자 요구를 모두 담았는지는 별도로 설명합니다.

## 실행하지 않은 검증 대상

검사를 실행할 때 어떤 코드 파일이 실제로 실행됐는지 함께 기록합니다. Python과 Node(`.py`·`.js`·`.mjs`·`.cjs`)를 관찰하며 하위 프로세스도 포함합니다. `status`의 검사마다 `unexecuted_watch`, 증명서의 `unverified_scope`에 **통과했지만 어떤 검사도 실행하지 않은 검증 대상**이 나옵니다.

훅이 주는 미완료 상태에도 같은 정보가 `unexecuted`로 들어갑니다. 작업 도중에 확인해 검사를 보완할지 판단합니다. 이 목록이 비어 있지 않으면 완료 보고의 미검증 범위에 그대로 적습니다. 통과한 검사가 바꾼 파일을 한 번도 실행하지 않았다면 검사를 보완할지 판단합니다. 값이 `null`이면 실행을 관찰하지 못했거나 관찰할 수 없는 언어가 범위에 있는 것이며(예: 셸·빌드 명령, TypeScript·Go·Rust 소스) 미실행을 주장하지 않습니다. 이때 `unobservable_watch`에 그 원인 파일이 나오므로, 검사를 나눠 관찰 가능한 범위만 따로 등록하면 나머지의 미실행 목록을 얻을 수 있습니다.

파일 단위 관찰입니다. 실행했다는 사실이 그 파일의 모든 동작을 검증했다는 뜻은 아니며, 줄·분기 수준의 커버리지도 아닙니다. 문서·설정 같은 비실행 파일은 이 관찰의 대상이 아닙니다.
