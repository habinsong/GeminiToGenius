# 코드 설계

설계는 지금 있는 요구와 호출자를 기준으로 판단합니다. "나중에 필요할지 모른다"는 이유로 만든 구조는 쓰이지 않은 채 남거나, 정말 필요해졌을 때는 모양이 달라서 다시 뜯어고치게 됩니다.

## 추상화를 만드는 때

같은 로직이 이미 두 곳 이상에 있고 앞으로도 함께 바뀌어야 할 때 공통 함수나 클래스로 묶습니다. 사용자가 확장 지점(플러그인 경계, 공개 인터페이스)을 분명히 요구했을 때도 만듭니다. 그 밖에는 구체적인 함수와 클래스를 바로 씁니다.

다음은 대부분 헛 추상화입니다.

- 구현이 하나뿐인 추상 클래스·인터페이스·Protocol
- 클래스 하나만 만들어 돌려주는 팩토리, 등록 대상이 하나뿐인 레지스트리
- 받은 인자를 그대로 다른 함수에 넘기기만 하는 함수, 모든 메서드가 그렇게 생긴 래퍼 클래스
- `Manager`, `Helper`, `Utils`, `Service`, `Handler` 같은 이름 아래 서로 관계없는 일이 모인 클래스
- 아무 코드도 읽지 않는 설정 옵션과 매개변수, "확장성을 위해" 남겨 둔 빈 훅

## 큰 파일과 클래스

새 책임은 그 책임만 가진 새 모듈에 둡니다. 이미 큰 파일(기본 400줄 초과)이나 메서드가 많은 클래스(기본 20개 초과)에는 새 기능을 더하지 않습니다. 버그를 고치려고 큰 파일의 몇 줄을 바꾸는 것은 괜찮지만, 요청받지 않은 대규모 재구성을 함께 하지는 않습니다. 정리가 필요해 보이면 보고에 제안으로 남깁니다.

나누는 것 자체가 목적은 아닙니다. 책임이 다르면 나누고 같으면 합칩니다. 함수 하나짜리 모듈을 여러 개 만드는 것도 헛 구조입니다.

## 미완성 코드

`pass`, `...`, `NotImplementedError`만 있는 함수, TODO·FIXME 주석, 고정값을 돌려주는 가짜 구현을 남긴 채 완료라고 하지 않습니다. 정말 남겨야 하면 보고의 미완성 항목에 이유와 함께 적습니다.

## 구조 검사

`structure`는 기준 리비전(기본 HEAD)과 작업 트리를 비교해서 이번에 바뀐 코드만 봅니다.

```bash
python3 "$GTG_RUNNER" structure --workspace /absolute/project/path
python3 "$GTG_RUNNER" structure --workspace /absolute/project/path --base START_COMMIT src/exporter.py
```

차단(`block`) 신호가 있으면 종료 코드 1입니다. 새로 넣은 줄의 TODO·FIXME, 본문이 빈 함수, 기준을 넘어 커진 파일, 메서드 수가 기준을 넘어 늘어난 클래스, 구문 오류가 여기에 들어갑니다. 검토(`review`) 신호는 구현이 하나뿐인 추상 클래스, 래퍼 클래스, 단순 전달 함수, 부르는 곳이 없는 새 정의, 길고 복잡한 함수이고 종료 코드에는 영향을 주지 않습니다. 검토 신호는 하나씩 보고 지우거나, 남기는 이유를 보고에 적습니다.

작업 중간에 커밋하면 기준이 움직이므로 시작할 때의 커밋 ID를 `--base`로 고정해 등록합니다. 큰 저장소에서는 바꾼 경로를 인자로 넘겨 범위를 좁히고, 생성된 파일은 범위에서 뺍니다.

```json
{"id": "structure", "criterion": "새 코드에 빈 구현과 미완성 표식이 없고 큰 파일·클래스에 기능을 쌓지 않았습니다.",
 "argv": ["python3", "/absolute/path/run.py", "structure", "--workspace", ".", "--base", "START_COMMIT"],
 "watch": ["src"], "timeout_seconds": 120}
```

한계도 알고 씁니다. Python은 AST로 정의·복잡도·응집도·빈 본문을 보지만 다른 언어는 줄 수와 주석 표식만 봅니다. 문자열로 조합한 동적 호출은 참조로 잡지 못하므로 `unreferenced` 신호만 보고 바로 지우지 말고 호출 경로를 확인하세요. 통과했다고 설계가 좋다는 뜻은 아니고, 검토 신호가 있다고 결함이라는 뜻도 아닙니다.
