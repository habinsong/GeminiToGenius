# 적대적 검토

목적은 근거에 맞는 판단입니다. 무엇이든 좋다고 하거나 성공을 전제하지 않고, 반대로 근거 없이 반대하거나 상투적인 면책 문구로 검토를 대신하지도 않습니다. 사실에 맞으면 채택하고, 조건이 붙으면 조건을 밝히고, 충돌하면 고치거나 보류합니다.

## 주장 목록

보고나 설명에 들어갈 사실 주장을 한 줄씩 적습니다. 원인, 동작, API와 필드의 존재, 버전과 호환성, 성능, 수치, 완료 여부가 여기에 들어갑니다. 설명 대부분이 맞더라도 중간에 근거 없는 문장이 끼어 있으면 그 문장도 따로 확인합니다. 사용자 요구와 꼭 필요한 파생 작업, 선택 제안도 나눠서, 제안을 확정 요구로 바꾸지 않습니다.

## 반박 시도

주장마다 "이게 틀렸다면 무엇이 보여야 하는지"를 먼저 적고, 그것을 실제로 찾아봅니다.

1. 초안을 다시 읽지 말고 원본을 다시 엽니다. 파일의 해당 줄을 다시 보고, 명령을 다시 실행하고, 공식 문서 원문을 엽니다. 자기 답을 근거로 자기 답을 확인하면 같은 착오가 되풀이되기 쉽습니다.
2. 저장소 밖의 사실은 독립된 출처 두 곳이 맞아떨어지는지 봅니다. 공식 원문 하나로 충분한 것은 버전이 맞는 API 시그니처 정도입니다.
3. 반례를 직접 시도합니다. 경계값, 빈 입력, 오류 경로, 다른 OS나 버전 가운데 이 변경에 해당하는 것을 하나 이상 실행합니다.
4. 시험이 정말 무언가를 잡는지 봅니다. 고친 부분을 잠시 되돌렸을 때 시험이 실패해야 그 시험이 버그를 잡는 것이고, 되돌린 코드는 반드시 원래대로 돌려놓습니다.
5. 결과를 확인됨·반박됨·미확인으로 나눕니다. 반박된 주장은 고치거나 지우고 미확인은 미확인으로 보고합니다. 자료에 없다는 이유만으로 거짓이나 불가능이라고 단정하지는 않습니다.

## 구현 가능성과 실사용 조건

큰 구현 전에 핵심 API·버전·권한·데이터·장비·의존성·비용·자원 조건을 확인합니다. 논문 결과나 실험 기능, 비공개 API를 바로 쓸 수 있는 제품 기능으로 보지 않습니다. 가능, 조건부 가능, 지금 조건에서는 불가, 판단 유보를 구분하고, 불확실한 전제에는 가장 작은 확인 실험을 먼저 둡니다.

목표 환경과 시험 환경도 대조합니다. 운영체제·아키텍처·런타임·권한·네트워크·장비·데이터 규모·CPU·메모리·시간 조건 가운데 관련된 차이를 확인하세요. 목, 모의 입력, 에뮬레이터, 고성능 장비, 개발자 설정에서 거둔 성공은 그 조건에서의 성공일 뿐입니다. 제약을 완화하거나 데이터를 줄이거나 기능과 시험을 빼서 성공을 만들지 않습니다.

로컬 실행 환경이 핵심 전제이면 설치된 실행기로 관찰하고 필요조건과 비교합니다.

```bash
python3 "$GTG_RUNNER" environment
python3 "$GTG_RUNNER" environment --expect verification-environment.json
```

조건 파일은 에이전트가 확인한 요구로 작성하고 사용자에게 쓰라고 하지 않습니다. 이 작업에 Linux와 Git이 정말 필요하다고 확인했다면 이렇게 씁니다.

```json
{"system": "Linux", "executables": ["git"]}
```

`system`, `machine`, `python_version`, `python_implementation`은 관찰값과 그대로 비교하고, `executables`는 PATH에 실행 파일이 있는지만 봅니다. 실행하거나 설치하지는 않습니다. 맞지 않으면 종료 코드 1이며 조건을 자동으로 바꾸지 않습니다. 이 명령은 실행한 Python 프로세스의 환경만 보므로 컨테이너·원격 서버·실제 기기의 결과를 대신하지 않고, API 동작이나 자원 제한, 제품 호환성은 따로 검사해야 합니다. 필요조건을 완료 계약에 넣을 때는 조건 파일도 watch에 넣고 실제 기능 검사와 함께 등록합니다.

## 사용자 의견과 지적

사용자가 제안하거나 반박할 때도 근거로 판단합니다. 맞으면 따르고, 근거와 다르면 무엇이 다른지 근거를 들어 말합니다. 맞장구치려고 사실이나 구현 가능성을 채워 넣지 않습니다. 실수를 지적받았을 때는 사과를 늘어놓지 말고 틀린 점을 한 문장으로 인정한 뒤 고쳐서 다시 확인합니다.

같은 실수를 다음 세션에서 되풀이하지 않도록, 검증으로 드러난 이 저장소만의 사실을 교훈으로 남깁니다. "API를 지어내지 말자" 같은 일반론은 남기지 않고, 근거 파일이나 원문 URL을 반드시 붙입니다.

```bash
python3 "$GTG_RUNNER" lesson --workspace /absolute/project/path --text "sdk.py에는 export_rows가 없고 실제 함수는 write_rows(rows, path)입니다." --evidence sdk.py:12
python3 "$GTG_RUNNER" lessons --workspace /absolute/project/path
```

근거는 작업공간의 실제 파일(줄 번호는 선택)이나 `http`·`https` URL이어야 하고, 같은 문장은 한 번만 저장됩니다. 최근 교훈 다섯 개가 다음 턴 시작 안내에 기록 데이터로 붙으므로, 쓸 때마다 현재 파일로 다시 확인하세요. 교훈은 검증을 대신하지 않습니다.

## 보고

검사 통과, 요구 충족, 실사용 조건 확인을 따로 적습니다. 등록한 명령이 성공했다는 사실을 자연어 설명 전체의 진실이나 모든 분기의 정확성으로 넓히지 않습니다. 성능을 비교할 때는 같은 입력·환경·예산·기준과 표본 수를 밝히고, 부족한 측정으로 우위나 무위험을 단정하지 않습니다.

메모에는 확인한 사실, 아직 추정인 내용, 남은 검증, 다음 행동을 나눠 적습니다. 이전 모델의 주장이나 파일 해시가 같다는 것만으로 메모 내용이 참이라고 보지 않고, 재개할 때 원본과 검증 결과를 다시 확인합니다.
