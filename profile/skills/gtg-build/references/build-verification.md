# 컴파일, 참조와 PRD 시험

코드가 그럴듯한 것과 실행되는 것은 다릅니다. 코드 동작, 타입과 공개 호출 관계를 바꾸는 작업은 파일 수와 관계없이 작업 계약을 등록하고 아래 절차를 적용합니다. 문답, 문구와 포맷만 바꾸는 작업에 빌드를 강제하지 않습니다. 사용자가 조사만, 수정만과 시험만 지시한 범위를 넘기지 않습니다.

## 변경 전에 확인할 것

1. 실제 빌드 설정과 패키지와 잠금 파일, CI, PRD, 기존 시험을 확인합니다. 대상 언어와 도구가 없는데 익숙한 명령을 지어내지 않습니다.
2. 바꿀 호출의 선언 위치와 공개 내보내기와 타입/시그니처와 설치된 SDK 버전과 플랫폼 조건과 실제 호출자를 확인합니다. 생성 API는 생성 원본과 생성 명령까지 확인합니다. 검색에서 이름이 한 번 잡히는 것은 선언이나 호출 가능성의 증거가 못 됩니다.
3. PRD의 수용 조건과 지정된 단위, 통합과 회귀 시험을 각각 실제 검사에 연결합니다. 없는 시험은 요구에 맞게 구현합니다. PRD가 없으면 있다고 꾸미거나 사소한 수정 때문에 새 PRD를 만들지 않습니다.
4. 최초 빌드와 관련 시험으로 기존 실패를 확인합니다. 이미 깨져 있던 부분과 새 변경의 오류를 구분하며 기존 실패 때문에 현재 변경을 검증했다고 보고하지 않습니다.

외부/기존 API를 이름만 추정해 호출하지 않습니다. 타입 오류를 없애려고 빈 함수와 상수 성공 반환과 가짜 필드와 과도한 캐스트와 오류 무시와 동적 우회와 시험 삭제를 넣지 않습니다. 요청된 새 API는 실제 선언, 구현, 호출자와 실패 경로를 함께 연결하는 정상 구현으로 완성합니다. 불확실한 외부 API는 가장 작은 실제 컴파일, 임포트와 호출로 먼저 확인합니다.

## 코드 완료 계약

전체 작업 계약의 `checks`에 실제 빌드와 필수 시험 명령을 정의하고 다음 `code_contract`로 연결합니다. 예시는 저장소의 `evals/fixtures/prd-build-api` 사례에만 맞는 구조이므로 다른 프로젝트에 그대로 적용하지 않습니다.

```json
{
  "code_contract": {
    "build_check": "build",
    "test_checks": ["prd-unit"],
    "requirements": [
      {"id": "BUILD-01", "source": "PRD.md", "checks": ["build"]},
      {"id": "UT-01", "source": "PRD.md", "checks": ["prd-unit"]},
      {"id": "UT-02", "source": "PRD.md", "checks": ["prd-unit"]},
      {"id": "UT-03", "source": "PRD.md", "checks": ["prd-unit"]}
    ]
  }
}
```

`build_check`는 별도의 빌드/타입/구문 검사 ID, `test_checks`는 비어 있지 않은 필수 시험 ID 목록입니다. 빌드를 먼저 나열합니다. `requirements`는 명시한 요구 ID, 실제 근거 파일과 연결된 검사 ID입니다. PRD가 없는 작업에서는 이 목록을 생략할 수 있습니다. 선언하지 않은 PRD 요구를 자동으로 추출하거나 전부 포함했다고 판정하지는 않으므로 원문과 대조합니다.

계약은 잘못된 검사 연결과 존재하지 않거나 링크인 PRD를 거부하고, 모든 검사 입력과 PRD를 공통 `watch`에 포함합니다. 실제 빌드와 잠금 파일과 SDK 선언과 제품 소스와 시험 등 결과에 영향을 주는 입력을 넣고 빌드 생성물과 캐시는 제외합니다. 범위 예산을 넘기면 실제 대상 모듈로 작업을 나누되 필수 입력을 몰래 제외하지 않습니다.

빌드가 현재 입력에서 성공하지 않았으면 필수 시험은 `blocked`입니다. `verify --check`와 `--all`도 이를 우회하지 않습니다. 빌드를 다시 실행하면 이전 시험 성공은 `stale`이 되므로 새 빌드 뒤에 재실행합니다. PRD나 입력이 바뀌어도 이전 성공은 무효가 됩니다. 증명서 재실행은 선행 빌드의 실패와 지문 불일치 뒤에 종속 시험을 실행하지 않습니다. 다만 구형 계약은 자동으로 바뀌지 않으므로 `code_contract_enforced: false`이면 이 연결은 강제되지 않습니다.

## 실제 실행과 필수 시험 누락

작업 초반에는 가장 작은 컴파일/타입 검사와 직접 실패한 시험부터 실행하고, 마지막에 PRD가 요구하는 전체 빌드 대상과 시험으로 넓힙니다. 바꾼 함수만 확인한 채 다른 모듈, 링크와 앱 대상의 실패를 그대로 두지 않습니다. 구문 컴파일, 타입 검사, 임포트/링크, 실제 기능 호출, 실기 시험은 서로 다른 근거입니다. Python 컴파일만으로 없는 함수와 필드를 검출했다고 주장하지 않습니다.

Python `unittest` 프로젝트에서는 해당 프로젝트 인터프리터로 설치된 실행기의 `unittest`를 호출할 수 있습니다. 아래는 앞서 명시한 사례 폴더에서만 유효한 시험 ID입니다.

```bash
python3 "$GTG_RUNNER" unittest --start-directory . --pattern test_export.py --require test_export.ExportTests.test_text_and_dimensions --require test_export.ExportTests.test_invalid_dimensions --require test_export.ExportTests.test_startup
```

이 명령은 실제 시험 프로세스의 결과를 확인하고, 실행 0개, 전부 skip, 필수 ID 누락과 필수 ID skip/expectedFailure, 조기 종료와 관측 누락을 통과시키지 않습니다. 필수 시험은 성공한 다른 시험으로 대신할 수 없습니다. 선택적 시험의 skip도 결과에 기록합니다. 새 임시 캐시 경로와 바이트코드 쓰기 금지로 현재 소스 대신 이전 `.pyc`가 실행되는 일을 막습니다. 관측 결과가 256KiB를 넘으면 실패하므로 큰 시험은 필수 ID를 보존한 여러 검사로 나눕니다. 시간 제한은 등록한 검사 명령의 `timeout_seconds`를 사용합니다. 시험 코드는 일반 프로젝트 코드 권한으로 실행되고, OS 샌드박스와 악성 코드 격리는 제공되지 않습니다.

다른 시험 도구는 프로젝트의 실제 실행기와 구조화된 결과를 확인합니다. 도구별 시험 수, ID, skip, 필터와 실패 종료 계약을 확인하고 Python 실행기로 다른 언어를 검사했다고 보고하지 않습니다. 준비되지 않은 SDK, 기기, 권한과 의존성 때문에 실행할 수 없으면 막힌 조건과 미실행 시험을 보고합니다. PRD를 완화하거나 가짜 구현과 모의 환경을 실제 시험 통과로 바꾸지 않습니다.

완료 보고에는 실제 빌드 대상과 실행 명령과 시험 수와 필수 ID 결과와 실패/skip/미실행과 미검증 범위를 기록합니다. 계약에 등록한 검사가 통과했다고 PRD 전체가 충족된 것은 아니므로 따로 확인합니다.
