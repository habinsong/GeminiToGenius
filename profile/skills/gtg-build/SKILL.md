# 개발과 재개

작업 등록·조회·재개의 실행기는 이 스킬 파일 기준 `../../run.py`입니다. 설치된 스킬의 실제 경로에서 확인한 뒤 `python3 <실행기 절대 경로>`로 호출합니다. 설치 패키지는 전역 `gtg` 명령이나 Python 모듈을 등록하지 않습니다.

사용자에게 작업 명세를 대신 작성하라고 요구하지 않습니다. 요청의 대상·원하는 결과·유지할 동작을 현재 코드·오류·테스트에서 확인합니다. 맥락이 부족해도 읽기 전용 조사를 먼저 수행합니다. 서로 다른 결과나 데이터 손실을 낳는 선택만 한 번에 필요한 정보로 질문합니다.

요청에 생략된 조건은 기존 호출자·API 계약·설정·데이터 예제로 확인합니다. 눈앞의 실패만 고치면서 정상 입력·예외 처리·입력 보존·다른 사용 경로를 망가뜨리지 않습니다. “알아서”라는 말로 배포 대상이나 삭제 범위를 추정하지 않습니다. 대상이 확인되고 안전하게 되돌릴 수 있는 작업은 반복 확인 없이 수행합니다.

코드 동작·타입·호출 관계를 변경하면 [컴파일·참조·PRD 시험](references/build-verification.md)을 적용합니다. 현재 선언·SDK 버전·시그니처를 확인하고 빌드·필수 시험을 `code_contract`에 연결합니다. 단일 파일 수정도 포함하며, 없는 API·필드·함수나 가짜 구현으로 오류를 숨기지 않습니다.

복잡한 변경·불확실한 핵심 전제·호환성·성능·기술 채택은 [비판적 검토](references/critical-review.md)를 먼저 적용합니다. 검토 결과는 실제 근거에 따라 긍정·부정·조건부로 판단하며, 사용자 의견에 대한 동조 여부만 검사하지 않습니다. 좋은 점을 찾으려고 사실이나 구현 가능성을 채워 넣지 않습니다.

서로 관련된 여러 파일을 읽어야 하면 호스트의 배치 읽기를 우선합니다. 배치 도구가 없거나 출력 범위를 명확히 다뤄야 할 때는 [코드 조회](references/code-intake.md)를 사용합니다. 잘린 출력이나 일부 줄을 파일 전체 확인으로 보고하지 않습니다.

컨텍스트 압축 뒤에는 현재 진행 문서와 등록 작업의 `status`를 다시 확인합니다. 새 세션에서 기존 작업을 이어갈 때는 `tasks`로 후보를 찾고 원래 목표·명세·메모를 확인한 뒤 `attach`로 연결합니다. 기존 작업을 이어가기 위해 `start`로 새 작업을 만들지 않습니다. 후보가 여러 개라 현재 요청의 대상을 특정할 수 없으면 필요한 구분만 질문합니다. 명령과 연결 조건은 [작업 계약](references/task-contract.md)을 따릅니다.

문구·포맷 수정은 관련 기존 검증으로 끝냅니다. 코드 동작 변경과 여러 번의 구현·검증이나 세션 재개가 필요한 작업은 [작업 계약](references/task-contract.md)에 따라 에이전트가 완료 조건을 등록합니다. 검증 명령은 저장소에 실제 존재하는 테스트·빌드·결과 검사만 사용합니다. `echo`, `true`, 임의 출력은 기능 검증이 아닙니다.

한 번에 검증 가능한 변경을 수행합니다. 오류가 나면 실패한 실행 경계와 실제 결과를 확인하고 필요한 수정만 합니다. 동일 실패를 정보 없이 반복하지 않습니다. 도중에 작업을 줄여 완료로 만들거나 검사를 삭제하지 않습니다.

등록한 작업을 완료로 보고할 때는 [작업 계약](references/task-contract.md)의 `certify`로 명령·종료 코드·파일 지문을 묶은 증명서를 만들고 경로를 알립니다. 통과하지 않은 검사를 완료로 적지 않습니다.

스킬 본문이나 파일 수로 품질을 증명하지 않습니다. 현재 파일 상태에 대한 검증 결과와 실제 요구 충족을 따로 확인합니다. 사용자 중단·필수 응답 대기·외부 한도는 작업을 일시 중단하고 구체적인 이유를 기록합니다. 사용자가 재개하면 이어서 작업합니다.
