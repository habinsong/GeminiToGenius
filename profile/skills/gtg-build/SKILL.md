# 개발과 재개

작업 등록·조회·재개와 검사의 실행기는 이 스킬 파일 기준 `../../run.py`입니다. 턴 시작 안내에 `runner` 경로가 있으면 그 값을 쓰고, 없으면 설치된 스킬의 실제 경로에서 찾아 `python3 <실행기 절대 경로>`로 부릅니다. 설치 패키지는 전역 `gtg` 명령이나 Python 모듈을 등록하지 않습니다.

## 시작

사용자에게 명세를 대신 쓰라고 하지 않습니다. 요청의 대상과 원하는 결과, 유지해야 할 동작은 현재 코드·오류·시험에서 찾고, 맥락이 부족해도 읽기 전용 조사부터 합니다. 서로 다른 결과나 데이터 손실로 갈리는 선택만 한 번에 묻습니다. "알아서"라는 말로 배포 대상이나 삭제 범위를 넘겨짚지 않고, 대상이 분명하고 되돌릴 수 있는 일은 다시 묻지 않고 진행합니다.

요청에 빠진 조건은 기존 호출자·API 계약·설정·데이터 예제로 채웁니다. 눈앞의 실패만 고치다가 정상 입력이나 예외 처리, 다른 사용 경로를 망가뜨리지 않도록 호출자를 따라가 보세요.

## 고치기 전에

버그는 실패하는 시험이나 재현 명령부터 만듭니다. 고친 뒤 같은 명령으로 통과를 확인하고, 할 수 있으면 고친 부분을 잠시 되돌렸을 때 그 시험이 다시 실패하는지도 봅니다. 그래야 그 시험이 정말 그 버그를 잡는다는 것을 알 수 있습니다.

쓰려는 함수·필드·옵션은 현재 선언과 설치된 버전에서 확인합니다. 절차는 [컴파일·참조·PRD 시험](references/build-verification.md)에 있고, 라이브러리 사용법이 버전에 따라 다르면 `gtg-research`로 원문을 확인합니다.

## 설계

새 클래스·모듈·추상화를 만들기 전에 [코드 설계](references/code-design.md)를 읽습니다. 구현이 하나뿐인 추상화와 인자를 넘기기만 하는 래퍼를 만들지 않고, 새 책임은 새 작은 모듈에 두며, 이미 큰 파일과 클래스에는 기능을 더 쌓지 않습니다.

## 검증과 완료

코드 동작을 바꾸면 [작업 계약](references/task-contract.md)에 따라 실제 빌드·필수 시험·`structure` 검사를 등록하고 `verify`로 실행합니다. 검증 명령은 저장소에 실제로 있는 시험·빌드·결과 검사만 씁니다. `echo`, `true`, 임의 출력은 기능 검증이 아닙니다.

오류가 나면 실패한 실행 경계와 실제 출력을 읽고 필요한 만큼만 고칩니다. 같은 실패를 정보 없이 되풀이하지 않고, 도중에 작업 범위를 줄여 완료로 만들거나 검사를 지우지 않습니다.

보고하기 전에는 [적대적 검토](references/critical-review.md)로 핵심 주장을 하나씩 반박해 봅니다. 등록한 작업을 완료로 보고할 때는 `certify`로 증명서를 만들고, 경로와 `replay` 판정을 그대로 알립니다. 통과하지 않은 검사를 완료로 적지 않습니다.

## 여러 파일 읽기와 재개

관련 파일을 여러 개 읽어야 하면 호스트의 배치 읽기를 먼저 쓰고, 없을 때 [코드 조회](references/code-intake.md)를 씁니다. 잘린 출력이나 일부 줄을 파일 전체를 읽은 것으로 보고하지 않습니다.

컨텍스트 압축 뒤에는 현재 진행 문서와 등록 작업의 `status`를 다시 확인합니다. 새 세션에서 기존 작업을 이어갈 때는 `tasks`로 후보를 찾아 원래 목표·명세·메모를 확인한 뒤 `attach`로 연결하고, 이어 하려고 `start`로 새 작업을 만들지 않습니다. 사용자 중단·필수 응답 대기·외부 한도에서는 이유를 기록하고 멈췄다가, 사용자가 재개하면 이어서 합니다.
